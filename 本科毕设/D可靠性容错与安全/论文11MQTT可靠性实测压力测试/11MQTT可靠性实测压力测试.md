## 一、preview/abstract（p.1）
### 痛点 / 已有方法为什么不行
- [[MQTT（消息队列遥测传输）]]（MQTT，Message Queuing Telemetry Transport：物联网里最常用的轻量级消息协议，好比快递驿站——设备把消息交给驿站，驿站按「地址」转交给订阅的人）因通信模型高效、支持低功耗设备和多变网络条件而在 IoT（Internet of Things，物联网：能联网互传数据的传感器与设备的总称）中广泛采用，但**在真实硬件、真实参数组合下"可靠性到底什么价"缺乏系统实测**（p.1）。
- 已有工作各只切一面：能耗 vs [[QoS（服务质量）]]（QoS，Quality of Service：MQTT 的三级「投递保证」，好比快递的三档保价——QoS 0 只管发、丢了不补，QoS 1 保证送到但可能重复投递，QoS 2 保证送到且恰好一次；级别越高越可靠也越慢，三级握手流程见本文第三节）的对比（QoS 0 比 QoS 2 省电 87%）、协议间对比（MQTT vs CoAP/WebSockets——CoAP 与 WebSockets 是另外两种物联网/网页常用的通信协议，此处作参照）、六个 [[Broker（消息代理）]]（broker：MQTT 架构中居中转发消息的服务器，发布方与订阅方互不直连、全靠它中转，类比快递中转仓）的压力测试对比等，但**没有一项工作在系统资源受限、网络负载、传输速率、报文大小、客户端队列容量、网络规模这些现实条件的宽组合下给出综合分析**（p.1–2）。
- 作者团队此前做医院无线病人监测（e-Health）系统时，"该选哪个 QoS 级别才能兼得高可靠与低时延"这个问题无现成答案，是本文的直接动机（p.2）。

### 新方法（一段话）
用 11 块常见单板机搭一个与外网隔离的有线千兆实验台，以 Eclipse Mosquitto（最常用的开源 MQTT broker 实现）为 broker，把 **QoS 级别、broker CPU 性能（人为掐算力测可靠性下限的手段，见 [[CPU 配额（CPU quota）]]——CPU 配额：给进程规定「最多能用多少算力」，好比让员工每天只干 4 小时活，用来逼出系统资源紧张时从哪里开始崩）、[[payload（消息载荷）]]（payload：消息里真正要传送的数据内容，类比快递纸箱里的「货物」）大小、发布频率、客户端数量、发布队列大小、[[TCP（传输控制协议）]] [[Nagle 算法（Nagle's algorithm）]] 开关（TCP，Transmission Control Protocol：互联网底层的可靠传输协议，MQTT 消息最终靠它送达；Nagle 算法是 TCP 的「攒单发货」优化——把小数据包攒一攒再发，省带宽但可能加大时延）**七个参数做全组合压力测试（共 1944 种配置 × 10 次重复、8700 万条消息，p.4），测 [[RTT（往返时延）]]（RTT，Round-Trip Time：一条消息从发出到收到确认的来回耗时，类比寄出快递到收到「签收回执」的时间）、[[丢包率]]（丢包率：发出的一批消息中没送达的比例，好比 100 件快递丢几件）与端到端发布延迟（自定义 [[Time Factor（时间系数）]] 指标，口径见第四节），给出 Mosquitto 在消费级硬件上的运行边界与 QoS 选型建议。

## 二、introduction 与 related work（p.1–2）
1. 相关工作的关键数字（p.1–2）：
    - Toldinas 等：**QoS 越高能耗越高，QoS 0 比 QoS 2 少耗能 87%**（RPi 4 做 broker + ESP-WROOM-02 做客户端，p.1）；
    - 文献 [7]（Chen 等 2020）：声称 **QoS 0 的 RTT 与抖动反而高于 QoS 1/2**——本文核心结论之一将与之相反（p.1）；
    - MQTT vs CoAP：CoAP 效率高但无投递保证且安全机制弱；轻流量下 MQTT 时延更低、重流量下 CoAP 更优；**启用安全（[[TLS（传输层安全协议）]]，Transport Layer Security：给网络连接套一层加密管道的标准协议，浏览器网址 https 里的「s」就是它）会增加带宽与时延**（p.1–2）；
    - Mishra 等对 6 个 broker 的深度压测：**Mosquitto 虽是非可扩展（单核单机）broker，却在 CPU、时延、消息率全部指标上综合最佳**——这是本文选 Mosquitto 的依据；其不足是未做参数变化（硬件资源、客户端配置）的细粒度分析（p.2）。
2. 本文贡献（p.2）：
    1. 常见 IoT 硬件上的真机评测 + 精心设计的实验台；
    2. 实际 IoT 应用场景下不同 QoS 可靠性级别的对比分析；
    3. **实证 RTT 随 QoS 级别升高而增大（QoS 2 最高、QoS 1 次之、QoS 0 最低），与 [7] 的结论相反**；
    4. 系统参数与 broker 硬件能力对投递性能影响的深入调查。
3. 核心问题的问法（p.2）：消费级硬件上 MQTT 能承载多大流量而不劣化？客户端数量影响多大？payload 大小如何影响丢包？各 QoS 级别如何平衡时延与可靠性？**broker 硬件最小能削到什么程度才不可靠？**

## 三、MQTT 的 QoS 机制（p.2–3）
1. **三类实体**（p.2）：Publisher（发布方）、Subscriber（订阅方）、Broker（居中协调）。基于 topic 的[[发布订阅模式]]（发布/订阅：发消息的人与收消息的人互不认识、互不直连，都只跟中转的 broker 打交道——类似报社只管把报纸交到邮局、订户向邮局订阅，双方互不见面），通信必须经由 broker 中转（p.2–3）。
2. **MQTT 内建的容错对策**（p.3）：keep-alive/heartbeat（保活心跳：客户端定期「报平安」，超时没消息 broker 就判定它掉线）、client take-over（同 ID 顶替：同一个客户端 ID 再次连入时，broker 踢掉旧连接、让新连接接管）、message queuing（消息排队：给掉线的订阅方暂存消息，等它回来再投）、message delivery guarantees（投递保证，即 QoS）——本文聚焦最后一项。
3. **三个 QoS 级别**（p.3）：
    - **At most once（QoS 0）**：只发一次，接收方不确认，丢失不重发——"fire and forget"；
    - **At least once（QoS 1）**：消息驻留出站队列直到收到 **PUBACK**；可重传，**接收端可能出现重复消息**；
    - **Exactly once（QoS 2）**：在 QoS 1 确认流程上加一步——PUBREC（Publish Received）→ 发方发 PUBREL（Publish Release）表示已从队列删除 → 收方回 **PUBCOMP**（Publish Complete）结束，**保证恰好一次**。
    - **为什么需要分级**：QoS 保证是发送实体（publisher 或 broker）与接收实体（broker 或 subscriber）之间逐段协商的，不是端到端属性；选型与应用场景紧耦合（p.3）：可靠网络、可容忍偶发丢失 → QoS 0；必须到达且可容忍重复 → QoS 1；不容忍重复 → QoS 2。

### 三个指标的定义（p.3–4）
1. **RTT**：客户端发出消息到收到 broker 最终确认的耗时。**测量口径按 QoS 分层**——QoS 1 收 PUBACK 的时刻、QoS 2 收 PUBCOMP 的时刻（应用层）；**QoS 0 无应用层确认，退而用 TCP ACK 包的接收时刻（传输层）**；用 Wireshark 抓包（p.3–4）。
    - **为什么需要**：把三种 QoS 放到可比口径上，同时如实承认 QoS 0 测的是下层往返、不是同一层的东西。
2. **Packet Loss**：publisher 发出的消息中 subscriber 未收到的百分比（p.4）。抓包用 Wireshark（抓包工具：把网卡上经过的每个数据包录下来逐个检查，像给网络装行车记录仪）。
3. **Time Factor**：实际发完全部消息的耗时 ÷ 理论最小耗时（每客户端消息数 ÷ 发布频率）。**TF = 1 即最优**，越大说明传输过程开销越大（p.4）。
    - **为什么需要**：RTT 是逐条时延，TF 刻画整批发布的端到端效率，两者配合才覆盖"及时性"。
4. 可靠性的工作定义（p.4）：e-Health 场景下可靠性 = **投递成功保证 + 最小时延**两者兼得；故刻意设置过载场景，观察可靠性从哪里开始劣化。

1. **QoS 结论**（p.4）：**RTT 随 QoS 单调上升**（3.38 → 20.06 → 53.45 ms，均值），握手次数是直接原因（QoS 0 发完就不管、QoS 1 一问一答、QoS 2 两问两答——握手次数越多，每条消息的固定开销越大）；**丢包率随 QoS 单调下降**（0.77% → 0.36% → 0.19%），且标准差收敛更明显（4.89% → 2.18% → 1.19%）——**高 QoS 用时延换确定性**。TF 变化相对温和：QoS 2 的 1.106 在 50 Hz 场景下折合约 **2.12 s** 额外发布延迟（p.4）。
   - **这条取舍曲线怎么读**：把 Table I 中 QoS 0/1/2 三行连成一条曲线——横轴是 QoS 级别（想买的可靠性），纵轴分别看 RTT 与丢包率：RTT 曲线一路抬头（3.38→20.06→53.45 ms），丢包率曲线一路下探（0.77%→0.36%→0.19%）；两条曲线合起来就是「可靠性按时延计价」的汇率表。选型时先问业务能容忍丢多少，再查曲线看要付多少时延。另外注意均值旁的标准差：QoS 越高长尾越重（QoS 2 的 RTT 标准差 ±236 ms），只报均值会低估最坏情况。
2. **客户端数是最猛的因素**（p.4）：1、2 个客户端近乎完美（TF 1.001、零丢包、RTT ~3 ms）；5 个仍可接受（TF 1.057，绝大多数配置零丢包）；**10 个客户端是拐点**：丢包升至 1.75%、RTT 均值 82.23 ms 但标准差高达 292.93 ms——长尾严重，个别配置远差于均值（p.4–5）。注意原文正文与 Table I 在个别均值上有 1 ms 级出入（正文 83.23 vs 表 82.23），以表格为准。
3. **payload 大小**（p.5）：125 kB 档丢包骤升至 **1.276%**（小/中 payload 仅 0.002%/0.038%），RTT 从 5.31 ms 涨到 **66.90 ms**——大 payload 是三档中唯一显著劣化的。
4. **发布频率**（p.5）：5 Hz 零丢包；25 Hz 起出现丢包（0.35%），50 Hz 达 0.97%；RTT 同步走高（3.98 → 19.86 → 53.06 ms）。
5. **broker CPU**（p.5）：63%→25% 之间劣化最陡（RTT 18.89 → 42.50 ms，丢包 0.29% → 0.89%）；TF 受影响最小（1.03–1.08）——**CPU 主要影响的是系统整体行为而非单一指标**。
   大白话：CPU 配额从 100% 掐到 63% 还扛得住，再往下掐就近「断崖」——算力不够时消息不只是变慢，而是直接丢（定量证据见下文 B 节）。部署教训：别给 broker 进程限算力。
6. **队列大小与 Nagle 几乎无影响**（p.5）：相关性热图（Fig. 2，p.5，**未提取**）显示 **Nagle 与性能指标相关性最低，队列次之**；**客户端数与 RTT 相关性最强**；payload 与频率次之，再次是 CPU。QoS 与丢包负相关、与 RTT/TF 正相关。完整细分结果在论文的在线补充表格（p.5）。
   - **图解（Fig. 2，未提取，按正文描述文字图解）**：这是一张相关性热图——行与列分别是七个实验参数与三个性能指标（RTT/丢包率/TF），格子颜色深浅代表两个量「是否一起变大变小」及相关强度（色标未提取，仅按正文转述结论，无法逐格复述）。怎么看：先扫颜色最极端的格子，那就是影响最大的因素。读图结论：客户端数×RTT 的格子最醒目（相关性最强），Nagle、队列的格子几乎中性。与毕设的关系：毕设做完参数扫描后可用同款热图一图汇总「哪个参数最值得优化」。

### B. 高载下的表现（p.5–6）
只看 10 客户端配置（唯一显著劣化的条件），Nagle 剔除（影响可忽略）；payload × 频率合并成复合参数 **Bandwidth**：12.5 kB@50 Hz = 50 Mbps、125 kB@25 Hz = 250 Mbps、125 kB@50 Hz = 500 Mbps（p.5；结果图 Fig. 3，p.6，**未提取**）。

   **图解（Fig. 3，未提取，按正文描述文字图解）**：该图画高载场景下的丢包对比——横轴为复合带宽档位（50/250/500 Mbps），组内按 QoS 0/1/2、CPU 配额与队列大小分列（原图样式未提取，仅按正文转述）。怎么看：同一带宽内先比三档 QoS 的高低，再横向看带宽加大后哪一档先崩。读图结论：带宽越大丢包越凶、QoS 越高越扛得住；但 50 Mbps 处出现「QoS 1 反而比 QoS 0 丢得多」的反常点，追根是 CPU 被掐到 25%（见下条）。与毕设的关系：毕设压测可用同款「带宽 × QoS × 资源限制」分组图呈现拐点。

1. **丢包最坏点**（p.5–6）：**500 Mbps + 最小队列（10 条）时，QoS 0 平均丢包峰值达 22.71%**（跨三种 CPU 配置平均）；QoS 1 居中、QoS 2 始终最低。
2. **反直觉例外**（p.5–6）：50 Mbps 带宽下，**QoS 1（队列 100）平均丢包 1.344%（1 万条丢 134 条）反而高于 QoS 0**；细查发现**丢包只发生在 broker CPU 被限到 25% 的配置**——劣化根源不是带宽不够，而是**宿主机资源被掐死，broker 处理不动进来的数据**（p.6）。
3. **CPU 是根因的定量证据**（p.6）：极端场景（500 Mbps、10 客户端、队列 10、Nagle 开、QoS 0）下，**把 broker CPU 从 25% 放开到 100%，平均丢包率从 43.60% 降到 0.42%，差两个数量级**。作者由此判定：**丢包不能归因于 Mosquitto 的 MQTT 实现，而是严苛运行条件所致——换其他 broker 在同等约束下结果类似**（p.6）。
4. **RTT 极值**（p.6）：QoS 2 峰值 **1815 ms**（仅在刻意高压场景）；同条件下 QoS 0 保持 **< 2 ms**。
5. **Time Factor 极值**（p.6）：500 Mbps + CPU 25% 时 **QoS 2 平均 TF = 5.35——实际用 107 s 发完理论 20 s 的量**；QoS 1 最坏平均 2.49；其余 QoS 在可接受范围。
6. **连接数 vs 聚合吞吐是两种不同的瓶颈**（p.6）：典型 IoT 部署是大量低带宽客户端。在近似带宽下（1.25 kB、QoS 1、Nagle 开、CPU 100%、队列 1000），**5 客户端@50 Hz 平均 RTT 2.085 s，而 10 客户端@25 Hz 升到 3.237 s**——**客户端管理（并发连接）本身有独立于带宽的开销**，与 Fig. 2 中"客户端数与 RTT 相关性最强"一致（p.6）。
7. **功耗**（p.6）：两个极端配置实测——最低（CPU 25%、1 客户端、1.25 kB@5 Hz）平均 **3.5 ± 0.5 W**，最高（10 客户端、125 kB@50 Hz、CPU 100%）平均 **5.0 ± 0.71 W**；均低于 Up Board 标称典型值 6.6 W（负载 13 W），原因是 Mosquitto 只用单核。

## 六、Lessons Learned 与结论（p.7）
1. **性能劣化的主因是宿主系统算力限制，不是 Mosquitto 实现本身**；MQTT 作为应用层协议**不能保证严格时效性**——时延受 broker 负载与网络状况影响（p.7）。
2. **安全攸关应用选 QoS 2**：丢包最低，其额外时延在真实应用中可忽略（高压条件不常见）；作者的 e-Health 系统（[2]）**已用 QoS 2 传输 ECG、心率、体温等关键生命体征**（p.7）。
3. **纠正 [7]**：隔离千兆网保证 RTT 不受外部网络效应污染（设备间平均端到端时延 0.233 ms，即 233 µs——提取文本把括号内单位误录为 "233 ms"，按数值换算应为 µs，存疑标注），**RTT 确实随 QoS 升高而增大**，与既有文献预期一致（p.7）。
4. **小消息率 + 小 payload（MQTT 绝大多数目标场景）用 QoS 0/1 更合适**——传输快、足迹小，只要连接稳定且可容忍偶发丢失/重复（p.7）。
5. 实际部署中**丢包更可能来自无线信道问题，而非协议低效或 broker 过载**（p.7）。
6. broker 宿主硬件功耗 3.5–5 W，与典型 IoT 能耗画像一致（p.7）。

### 局限（p.6–7，我的检视）
- 单一 broker 实现（Mosquitto）+ 有线网，**未测 TLS、broker 集群与无线链路**——而结论恰恰说真实丢包来自无线，这两者之间有实测空白；
- 最多 10 客户端是 **"高带宽少客户端"型压力**，"多客户端低带宽"型只做了对比实验，未扫连接数上限；
- RTT 在 QoS 0 用 TCP ACK 口径，与 QoS 1/2 应用层口径**不完全同层**，对比时要注意。

## 对毕设的帮助
**写论文**：
- 「性能测试/可靠性设计」章节可引用的结论数字（注明出处与口径）：RTT 随 QoS 单调上升（3.38/20.06/53.45 ms 均值）且丢包率随 QoS 单调下降（0.77%/0.36%/0.19%）；10 客户端拐点（丢包 1.75%、RTT 82.23±292.93 ms，长尾显著）；payload 125 kB 档丢包骤升至 1.276%；broker CPU 25%→100% 使丢包 43.60%→0.42%（差两个数量级）；TF 最坏 5.35（500 Mbps、CPU 25%、QoS 2）；broker 宿主功耗 3.5–5 W。
- RTT 测量口径必须按 QoS 分层写清楚（QoS 1 用 PUBACK、QoS 2 用 PUBCOMP、QoS 0 用 TCP ACK，Wireshark 抓包），避免重蹈文献 [7] 的层间混淆；Time Factor（实际/理论最短发布时间）可作为毕设性能测试章节的自定义指标引入。
**动手实现**：
- 关键数据（若毕设含告警/控制类消息）选 QoS 2，小报文遥测选 QoS 0/1；**丢包先查 broker 宿主 CPU 再怀疑协议**（CPU 25%→100% 丢包 43.6%→0.42%），边缘网关不给 Mosquitto 进程设 CPU 限制；队列大小在 10–1000 内影响不大，持久化队列按默认即可；keep-alive、client take-over、message queuing 是 MQTT 自带的可靠性机制，毕设的断线重连方案应建立在这三者之上。
**测试**：
- 直接照抄测试矩阵与测法：QoS{0,1,2} × payload{1.25k/12.5k/125 kB} × 频率{5/25/50 Hz} × 客户端{1/2/5/10} × 队列{10/100/1000} × Nagle{开/关}，每客户端固定 1000 条、每配置 10 次重复，Wireshark 抓包测 RTT。
- 多节点组网测试扫到 5→10 客户端量级（客户端数是与 RTT 相关性最强的因素，**5→10 客户端是消费级硬件上的拐点**），指标报「均值±标准差」以暴露长尾（长尾由 QoS 握手放大，只报均值会掩盖）；"同等带宽下客户端越多 RTT 越高"提示测试要区分**聚合吞吐瓶颈**与**连接管理瓶颈**两类场景分别设计；边缘网关功耗预算可参照 broker 宿主 3.5–5 W。

## 怎么用 & 怎么做（研0 版落地清单）

> 思维导图：[[11思维导图.canvas]] · 总览：[[毕设论文总导图.canvas]]

**什么时候翻这篇**：任务 6 执行性能测试阶段（测试矩阵与指标口径逐项照抄）；分析结果时（归因顺序：先查 CPU 再怀疑协议）；写部署建议时（QoS 选型与功耗数字）。

**在 Ubuntu 22.04 上**：
- CPU 配额实验复现（p.5）：`systemd-run --scope -p CPUQuota=25% mosquitto -c /etc/mosquitto/mosquitto.conf`，25%/63%/100% 三档跑同一负载——预期复现「CPU 25→100% 丢包 43.6%→0.42%」的量级。
- 队列参数对照（p.3）：mosquitto.conf 里 `max_queued_messages 10/100/1000` 三档。
- RTT 抓包口径按 QoS 分层（p.3–4）：QoS 1 看 PUBACK、QoS 2 看 PUBCOMP、QoS 0 退用 TCP ACK——`tshark -Y 'mqtt.msgtype==4'` 过滤；结果报「均值±标准差」暴露长尾。

**在树莓派上**：
- 复刻实验台（p.3）：树莓派集群当 publisher（台数不够用多进程补）、一台机器当 broker + subscriber，全接同一台交换机的隔离网段（不连公网，排除无线误码干扰）。
- 每 publisher 固定发 1000 条、每配置重复 10 次；优先扫「客户端数 1/2/5/10」（本文最强因素），在 5→10 之间找你硬件的拐点。

**C++ 实现要点**：
- broker 部署纪律（p.6 教训）：不给 broker 进程设 CPU/内存限制；丢包出现先查宿主资源（`top`/`vmstat`）再怀疑协议实现。
- 发布端限速用令牌桶；keep-alive、同 ID 顶替（client take-over）、离线排队是 MQTT 自带机制，断线重连方案建立在这三者之上（p.3），别重复造轮子。
