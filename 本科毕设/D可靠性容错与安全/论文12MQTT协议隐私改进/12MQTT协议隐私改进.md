## 一、introduction and motivation（p.1–2）
### 痛点 / 已有方法为什么不行
- [[MQTT（消息队列遥测传输）]]（MQTT，Message Queuing Telemetry Transport：物联网里最常用的轻量级消息协议，好比快递驿站——设备把消息交给驿站，驿站按「地址」转交给订阅的人）为资源受限设备设计（发布一条消息的协议开销最好情况仅 **2 字节**），是 IoT（Internet of Things，物联网：能联网互传数据的传感器与设备的总称）最常用的[[发布订阅模式]]（发布/订阅：发消息的人与收消息的人互不认识、互不直连，都只跟中转服务器打交道——类似报社→邮局→订户，双方互不见面）协议；公开可用的 [[Broker（消息代理）]]（broker：MQTT 架构中居中转发消息的服务器，类比快递中转仓；public broker 即任何人都可连的公共 broker）让 NAT（Network Address Translation，网络地址转换：让家里多台设备共享一个公网 IP 上网的技术；NAT 内的设备没有独立「公网门牌号」，外面的主动连接进不来）内网设备无需改网络配置即可与外界交换消息（p.1）。
- **核心问题（Problem）**：broker 为了决定向谁转发，**必须能读消息的 [[Topic（主题）]]，因此 topic 无法像 [[payload（消息载荷）]] 那样加密**。Topic（主题）：消息的「地址标签」——发布方把它贴在消息上，broker 按它决定转给谁，如 `livingroom/switch/off` 表示「客厅/开关/关」；payload 则是消息正文本身——好比信封上的地址 vs 信纸里的内容。broker 要按地址分信，就必须看得见地址，所以 topic 天生对 broker 明文，这就是「topic 不能加密」的根本原因。broker 即使不碰 payload 内容，也能凭 topic 做用户画像——论文给的例子：`livingroom/switch/off` 这一 topic 就能推断作息（睡眠习惯）；**"知道某个开关被拨动"本身就是隐私数据**（p.1）。
- **为什么这是「元数据隐私」问题**：topic 属于 [[元数据（Metadata）]]——元数据指「关于数据的数据」：不是信纸里的内容，而是信封上的地址、邮戳、寄件时间这类外围信息（谁、在何时、用什么标签、发了多大一条消息）。payload 加密再严，通信的「形状」（topic、时机、频率、大小）仍然可见，而 IoT 场景里这些形状本身就足以还原生活习惯——本文 p.1 的作息推断就是一例。**元数据隐私**正是本文的主题词。
- payload 可做[[端到端加密（End-to-End Encryption）]]（端到端加密：只有收发两端能解密，中间任何节点——包括 broker——看到的都是密文；好比只有寄件人和收件人有钥匙的挂号信，快递员只送信封、看不到内容）已有成熟方案（[[TLS（传输层安全协议）]]、ABE 等——TLS，Transport Layer Security：给网络连接套一层加密管道的标准协议，浏览器网址 https 里的「s」就是它；ABE：按「属性条件」控制谁能解密的加密方式，本文不展开），**topic 这一层的隐私是空白**；且已有方案（SecKit、ACL、PAKE 会话密钥——均为已有的 MQTT 安全加固方案名）都要把信任押在 broker 上——见下节（p.1–2）。

### 新方法（一段话）
作者的核心论点：**topic 不必是有意义的词**——只要所有客户端对同一消息类型使用相同的（混淆后）topic，转发就不受影响。于是问题化为"两个以上客户端如何在不让任何第三方知道的前提下协商一套混淆方案"。论文给出**五种 topic 混淆策略**（全部只改客户端、不改 broker、兼容 MQTT 标准），并实现其中最有希望的 **AOTP**（进阶一次性口令），在真实公网 broker 上实验验证其对时延的额外开销相对网络时延可忽略（p.1）。

## 二、related work（p.2）
| 已有方案 | 机制 | 为什么不够（p.2） |
|---|---|---|
| SMQTT [9] | 基于属性加密 ABE + 轻量椭圆曲线；payload 用 AES、AES 密钥用 ABE 加密 | **只加密 payload，topic 仍可被 broker 读取** |
| SecKit [7] | 安全策略规则执行，集成在 MQTT 协议层 | **必须集成进 broker，客户端得信任 broker** |
| ACL 智能家居 [10] | 用 Mosquitto 的 ACL 控制消息流 + SSL | SSL 不是端到端，**broker 仍能读 topic 甚至内容** |
| PAKE 方案 [4][8] | 增强 PAKE 算法在 broker 与客户端间交换会话密钥 | 只保护 broker–client 链路，**broker 仍能读 topic** |
| Kraijak 等 [6] | 指出恶意用户可向 topic 发布假数据被他人消费 | 只提出问题，无解决方案 |

**本文的差异化定位**：所有方法**只在客户端侧执行**——因此**任何（哪怕不可信的）公网 broker 都能用**（p.2）。

## 三、五种隐私增强方法（p.2–4）
> 共同前提：所有方法**不修改 MQTT 标准**，可用于任何已部署的公网 broker；聚焦 topic，不管 payload（p.2）。

### A. 在 Payload 中重定义（Redefinition in the Payload，p.2）
- **含义**：消息链式换题——第一条在真 topic（如 `room/light/switch`）上发布，加密 payload 为 JSON `{t: "下一跳随机 topic", p: 真payload}`；此后每条消息都在上一条 payload 里指定的随机 topic 下发布，并再携带下一跳（Table I 给了两条消息的示例，p.2）。接收方只需跟着订阅新 topic。
- **为什么可行**：新 topic 只出现在加密 payload 里，broker 看不到对应关系；必须用足够高的 [[QoS（服务质量）]]（QoS，Quality of Service：MQTT 的三级「投递保证」——QoS 0 丢了不补、QoS 1 保证送到但可能重复、QoS 2 保证恰好一次，越高越可靠也越慢；实测代价见 [[11MQTT可靠性实测压力测试]]）保证链不断（丢一条就丢后续 topic）。
- **缺点**（p.2）：① 中途加入、错过第一条的客户端**永远无法得知后续随机 topic**；② broker 若懂此套路，可把"刚收到 A topic 消息的客户端紧接着订阅随机 topic B"关联为同一消息类型；③ payload 套 JSON 后二进制内容需 Base64，**体积 +33%**，且每条消息都要多带一个新 topic，消息变大。

### B. 同步随机主题（Synchronous Random Topics，p.2–3）
- **含义**：两个以上客户端共享**同一个[[伪随机函数（PRF）]]**（PRF，Pseudo-Random Function：给定一个「种子」就能产出一串看似随机、实则双方用同一种子能算出一模一样结果的函数——好比两人拿同一本密码本各翻各的页，翻出的「随机数」完全同步；seed 即种子，PRF 的初始输入）（同 seed 同步）。双方场景用 **[[Diffie-Hellman 密钥交换（DHKE）]]** 传 seed（DHKE：两人在公开信道上互发几个数字，最后各自算出同一个只有他俩知道的密钥，偷看的人推不出来——好比两人当众对暗号，旁观者听得见过程却猜不出暗号本身）；多方或无法 DHKE 时用预共享密钥（预共享密钥：双方事先通过线下/安全渠道约定好的同一把密钥）+ 对称加密（如 AES——对称加密：收发双方用同一把钥匙加解密的算法）传。**每种消息类型各配一个独立 PRF**。发布方用 PRF 生成 topic 发布；接收方收到消息后用 PRF 生成下一个 topic 并去 broker 订阅，如此滚动（p.2）。
- **代价与弱点**（p.2–3）：消息本身不增大（混淆 topic 与原 topic 等长时），但**要额外交换同步信息并反复重新订阅**；broker 可检测"收到消息后立刻订阅新 topic"的行为模式把多个 topic 归为同一类型——缓解办法是接收方若能估计消息间隔，就**延迟一段时间再订阅**。只在两客户端时最优雅（DHKE），多方需预先交换密钥材料，在 IoT 环境里这可能本身就很麻烦（p.3）。

### C. 批量随机（Mass Random，p.3）
- **含义**：B 的去模式化扩展。在共享 PRF 的基础上，为每种消息类型 t 选常量 $c_t$，用同步的 PRF 生成大小为 $c_t$ 的**同义词 topic 集合** $S_t$；消息类型少时再加一包**哑 topic 集** $S_0$；每个随机 topic 的**每一层级等长**（用 hash 函数 $F$ 与占位符补齐层数与长度——hash 函数：把任意输入压成一串固定格式的「指纹」，同输入必得同输出，但极难从指纹反推输入），防止按长度分类。全部集合合并 $S = S_0 \cup \bigcup_t S_t$、**随机打乱后一次性订阅**，$S_0$ 用后即弃。发布方从对应 $S_t$ 里**随机挑一个**发布；接收方在 $S_t$ 里查表还原原 topic（p.3）。
- **为什么需要**：消灭了 B 的"每收一条就重订阅"的可检测模式；混合订阅 + 哑 topic + 等长 topic 让 broker 在订阅阶段难以归组。
- **残余风险**（p.3）：运行期 broker 仍可随时间按**使用频率/使用时段**做统计分类；$c_t$ 应按该类型的发布频率选取，防止同一同义词用得太频繁；仍需预先同步 PRF。

### D. 一次性口令（OTP，p.3–4）
- **含义**：受[[一次性口令（OTP）]]（OTP，One-Time Password：一次性口令/动态密码——每个口令只用一次、用完作废，如网银短信验证码）启发的**[[hash 链（Hash Chain）]]**（hash 链：把同一个 hash 函数反复套用得到的一串值——上一环的输出是下一环的输入；好比反复折纸，每道折痕都依赖之前所有折痕，无法跳步伪造，也难从最后一道折痕反推全链）方案。前提：客户端间已有安全信道（预共享密钥加密消息），共用 hash 函数 $F: \Sigma \to \{a{-}z, A{-}Z, 0{-}9\}^*$（这个记号读作：$F$ 把任意输入 $\Sigma$ 映射成由大小写字母和数字组成的字符串）。发送方为每个要用的 topic $t$ 准备 hash 链表 $H_t$：
$$H_t = \{F(s),\ F(H^1_t),\ F(H^2_t),\ \dots,\ F(H^{n_t-2}_t),\ F(H^{n_t-1}_t)\}$$
（$s$ 为随机字符串，链首元素是 $F(s)$，每个后继是前驱的 hash，链长 $n_t$ 按内存自选。）
    - **逐符号读这条公式**：$H_t$ 是 topic $t$ 的「一次性口令链表」；$F(\cdot)$ 是 hash 函数（见 C 方案的解释）；$H^i_t$ 的上标 $i$ 表示链上第 $i$ 个中间值；$n_t$ 是这条链的长度（能用多少次）。链上每一项都是「把前一项再 hash 一次」：$F(H^1_t) = F(F(s))$、$F(H^2_t) = F(F(F(s)))$，环环相扣。**大白话**：这是一串环环相扣的「指纹」，发布方每发一条消息就用掉一环充当 topic 并把这环删掉；接收方把收到的口令再 hash 一次，正好得到链上的下一环，拿它与自存的对照表核对——对上就说明口令出自「自己人」，随后把表更新到当前环、等下一次比对。没参与生成这串链的人既猜不出下一环，也无法从已公开的环反推尚未使用的环（hash 难逆）——这就是「一次性」防伪造与防重放的原理。发送方另选随机**前缀 $p$**，经预定义 topic 把加密消息 $m = \{p,\ M: t \mapsto H^{n_t}_t\ \forall t \in T\}$（前缀 + 映射表）发给所有合法客户端。此后每发布一条 topic $t$ 的消息，用混淆 topic $p/H^{n_t-1}_t$，**同时删掉链尾元素并把 $n_t$ 减一**（一次性口令的"一次性"来源：每个 hash 值只用一次）（p.3）。
- 接收方（p.3）：事先用通配符 `p/#` 订阅一切带该前缀的消息（通配符：MQTT 订阅时可用 `#` 匹配任意多层后缀、`+` 匹配任意一层，类似搜索里的星号 `*`，用于「一次订阅一片」）；收到后剥掉前缀得 $\tau$，算 $h = F(\tau)$，在映射 $M$ 里查 $h$ 对应哪个 topic——查到就把映射替换为 $t \mapsto \tau$（记录当前链位置），查不到就忽略该消息。
- **配套设计**（p.3–4）：① 经预定义 topic 可实现 **m 的请求机制**，晚加入的客户端也能拿到映射参与进来；② 内存紧张的发送方可只存 $s$、$p$、$n_t$，每次发布现算链（每条消息要做 $n_t$ 次 hash）——**更耗能量，不适合电池设备与实时应用**；③ **前缀碰撞反而是特性**：两方撞了同一前缀时 broker 会转来"错"的消息，接收方解不开就忽略，但这**增加了 broker 关联通信双方的难度**；想人为制造碰撞，可借用常用 topic 的第一层做前缀——作者观测某公网 broker 上 48 小时内约 **140 万条**消息的 topic 以 `iot/` 开头（p.3–4）。按上下文推断，`iot/` 被论文判定为坏前缀：撞上如此高频的流会让接收方不断收到并浪费算力去解无关消息（原文此句推理很简略："The attempt to de-obfuscate a message topic requires time and energy, so the prefix iot/ is obviously no good choice."）。
- **残余风险**（p.4）：topic 从未明文出现在 broker，但**若用标准化 hash 函数，数据分析者可能识别出该套路并把对应消息关联起来**——所以需要"完全随机化的混淆"，引出 E。

### E. 进阶一次性口令（Advanced OTP，AOTP，p.4）——本文实现并评估的方案
- **含义**：[[AOTP（进阶一次性口令）]]，Advanced OTP——OTP 的加盐升级。hash 函数改为 $F: \Sigma \to \mathbb{Z}$（映射到整数），配 $str$（hash 值转字符串，如十六进制）与 $num$（字符串转回 hash 值）两函数；另选**随机多项式 $P$**、随机串 $s$ 与前缀 $p$。hash 链改为**隔项掺盐递推**：
$$H^1_t = F(s), \qquad H^i_t = F\big(H^{i-1}_t \cdot P(i)\big) \quad 2 \le i \le n_t$$
- **逐符号读这条公式**：$H^i_t$ 是 topic $t$ 的链上第 $i$ 环；$F$ 此处是把输入映射到整数的 hash 函数（$\mathbb{Z}$ 即整数集合）；$P$ 是随机多项式（输入位置 $i$、输出一个数）；$\cdot$ 是乘法；$s$ 是随机起始串；$2 \le i \le n_t$ 表示递推从第 2 环算到第 $n_t$ 环。**大白话**：和普通 hash 链一样环环相扣，但每生成新一环前，先给上一环「掺一把盐」——乘上 $P(i)$（盐随位置 $i$ 变化）再 hash。掺盐让两条哪怕从同一个数出发的链也走向完全不同，分析者更难断言「这两串数字是一伙的」；这就是 AOTP 相对 OTP 的「进阶」之处。
发布消息用 topic $p/str(H^{n_t-1}_t)$，发布后删链尾、$n_t$ 减一。初始消息改为 $m = \{p,\ M: t \mapsto H^{n_t}_t,\ P,\ n_t\ \forall t\}$（多传 $P$ 和各链长）。接收方剥前缀、$num(\tau)$ 得整数，对 $M$ 中每个候选映射**逐个尝试** $h = F(\tau) \cdot P(n_t)$ 直到命中，命中后更新映射与链长（p.4）。
- **为什么需要多项式 $P$**：$P(i)$ 相当于**逐位加盐**，使数据分析者更难把两个 hash 值关联起来。可简化为每项乘同一个常数盐；也可**每种消息类型用不同多项式**，进一步加大跨类型分析的难度（p.4）。
- 前缀 $p$ 的作用（p.4）：过滤无关消息、减少无谓的解混淆尝试；与其他方共享前缀可制造碰撞、防 broker 定位通信双方——需要权衡。
- **解混淆流程图**（Fig. 4，p.5，本篇唯一提取图，见下）：逐个遍历映射 $M$ 中的候选 topic，对每个候选算 $h = F(\tau) \cdot P(x)$（$x = n[t]$ 为该类型当前链长）与存储值比对，命中返回 $t$，遍历完未命中返回 $\emptyset$——**"试错法"，最坏要算 $|M|$ 次 hash，最好 1 次**（p.5）。
- **通俗串讲 AOTP（研0 版）**：把 topic 想成信封上的地址，broker 靠地址分信、所以地址无法加密。AOTP 的思路是「地址不用真词、用一次性暗号」：① 发送方为每种消息类型生成一串环环相扣的 hash 暗号（每生成一环掺一把随位置变化的「盐」，外人更难把暗号两两关联）；② 开局先用一条加密消息把「暗号对照表 + 多项式 + 各链长」发给所有合法接收方；③ 之后每发一条消息，就用掉一个暗号充当 topic，并把链缩短一格——broker 全程只见无意义的随机字符串，且每个暗号只用一次、用完作废；④ 接收方用 `p/#` 通配符订阅本前缀的一切消息，收到后剥前缀、拿暗号到对照表里逐个「加盐再 hash」试错，对上就还原真 topic 并把表推进到下一环。代价是试错开销：最坏要把表里每个候选都算一遍（39 个 topic 的实测约 1–13 ms，见第四节）。

**图解**：这张流程图画的是接收端「解混淆」的判断链：收到消息 → 剥掉前缀得到暗号 τ → 对映射表 M 里的每个候选 topic 逐个尝试——计算 $F(\tau) \cdot P(x)$（$x = n[t]$ 为该类型当前链长）与表内存储值比对 → 命中就返回真 topic $t$，全部试完仍不中就返回空 $\emptyset$（忽略这条消息）。怎么看：沿箭头走「取一个候选 → 计算 → 比对 → 命中？下一个」的循环，循环嵌在「遍历 M」里。**读图结论**：解混淆本质是试错法，耗时取决于真 topic 在表中的位置——最坏要试 $|M|$ 次、最好一次命中；这正是后文实验「逐 topic 耗时差异明显」与「按频率重排映射可优化」的根源。**与毕设的关系**：毕设若实现 topic 隐私模块，此图就是接收端伪代码骨架，可照此实现再优化遍历顺序。

## 四、evaluation（p.4–6）
### 实验设置（p.4）
- 实现：**AOTP 方法**用 Python + Eclipse Paho MQTT 库；两部分——发送端生成 hash 链、发布映射消息 $m$，然后每次从 **39 个预定义 topic 池**随机取一个类型发布；接收端解混淆 topic。代码开源于 GitHub（github.com/mafmcfly/aotp-mqtt，p.4, 6）。
- broker：**公网 Eclipse Mosquitto 实例 iot.eclipse.org（MQTT 3.1）**与本地同软件实例对照（作者注明不认为 Eclipse 基金会真的在收集画像，但公网 broker 场景正是方案的目标，p.4）。
- 硬件：**Raspberry Pi 2 Model B**，收发两端跑在同一块板子上，免除时钟同步问题；delay 定义 = 发布时刻 → 接收端解混淆完成可用时刻（payload 就是发布时间戳，p.4）。
- **实验规程**：4 种组合（AOTP 远程 / AOTP 本地 / 明文 topic 远程 / 明文本地），**每 10 分钟一轮、连续 4 天**，每轮发 10 条消息；**每种组合执行 3800+ 次**（p.4）——用长时程采样抹平 broker 负载波动。

### 结果（p.4–6）
1. **本地 vs 远程（Fig. 1，p.5，CDF，未提取）**：远程公网 broker 明显慢于本地实例；**75% 的消息 topic 在本地十分之一的时间内就可用**——**网络传输开销远大于 RPi 上的解混淆开销**（p.4–5）。
2. **混淆 vs 明文（Fig. 2，p.5，CDF，未提取）**：明文本地时延 < 5 ms，其中 **3.7 ms 来自 broker + loopback（回环接口：本机进程连「本机自己」的虚拟网络接口，用来测出不径网络的基线时延）通信**；AOTP 本地最小时延约 5 ms，**减去 3.7 ms 基线后最快解混淆约 1 ms**；50% 的解混淆落在 **10–15 ms** 区间；对照 Fig. 1，**解混淆约只占远程 broker 全程时延的 10%**（p.4–5）。
   - **图解（Fig. 1/Fig. 2，未提取，按正文描述文字图解）**：两张都是 CDF 图（CDF，Cumulative Distribution Function，累积分布函数：横轴是耗时，纵轴是「耗时不超过横轴数值的消息占比」；曲线爬升越靠左越快，从曲线上可直接读出「百分之多少的消息在多少 ms 内完成」）。Fig. 1 叠画远程/本地两条曲线：远程整体右移——网络传输开销远大于 RPi 上的解混淆开销；Fig. 2 叠画明文/AOTP 两条曲线：明文贴近 3.7 ms 基线，AOTP 只右移一点点——解混淆只占全程约 10%。与毕设的关系：毕设测时延建议报告 CDF 或 P50/P75/P95 分位数，比单报均值更能暴露长尾。
3. **微控制器代价（p.5）**：ESP8266 上解混淆平均 **120 ms**——"粗略地说，AOTP + 远程 broker 的总时延在此类设备上翻倍"；但作者指出实际部署中 MCU 通常只负责采集并发布，**解混淆发生在无约束设备上**，故不构成障碍。
4. **按 topic 的分布（Fig. 3，p.6，直方图，未提取）**：39 个 topic 的纯解混淆时间大致在 **1–13 ms**（不含 broker 时延）之间，**且逐 topic 差异明显**——根因是试错法：解混淆耗时取决于该 topic 在映射 $M$ 里的位置（p.5–6）。
   - **图解（Fig. 3，未提取，按正文描述文字图解）**：直方图——横轴 39 个 topic（逐根柱子），纵轴该 topic 的解混淆耗时；柱子参差不齐（1–13 ms），因为试错法下耗时取决于该 topic 排在映射表的位置。与毕设的关系：测「逐通道/逐类型」的耗时分布可定位类似的结构性开销。
5. **优化方向（p.5）**：真实场景中各 topic 发布频率不均，可**按频率重排映射，高频 topic 排前面试**——发送方若预知频率就在 $m$ 里发布有序表，否则接收方**边观察边在线建序**。
6. 结论（p.6）：**AOTP 的解混淆开销只是网络时延的一小部分**；即使在 ESP8266 上解混淆耗时也只与消息传输时间相当——**方案适合大多数真实场景**。

## 五、conclusion（p.6）
- 用公网 broker 的价值：**免 NAT 改造、免自建服务器**（p.6）。
- 代价：topic 必须对 broker 可读 → 隐私暴露；本文五种混淆策略保住公网 broker 场景的隐私，其中 **AOTP（逐 topic 的迭代 hash 链）已实现并验证**：解混淆时间只是网络时延的零头，解混淆耗时随 topic 在映射中位置波动大，**按频率优化遍历顺序可显著改善**（p.6）。

### 局限（我的检视，p.1–6）
- 混淆 ≠ 加密： broker 仍可做**统计侧信道分析**（频率、时段、订阅行为），C/D/E 只是抬高分析门槛，论文未给出对抗统计攻击的定量评估；
- 五种方法都依赖**客户端间预先有安全信道**（PRF seed / 预共享密钥的交换），这一步如何引导（bootstrap）在 IoT 里未讨论；
- 评估只测了**时延单一指标**：消息体积（A 方案的 +33%）、订阅流量增加、内存占用均未量化；39 个 topic 池也偏小，试错开销随 topic 数线性增长的最坏情形未实测。

## 对毕设的帮助
**写论文**：
- 协议调研章节：写清「**payload 可端到端加密而 topic 必须明文给 broker**」——这是 TLS 保护不了的元数据泄露面；公网 broker 的价值（免 NAT、免自建）与代价（broker 可画像）一并记录。
- 可引用的数字：A 方案 payload 套 JSON 后体积 +33%；AOTP 解混淆在 RPi 上 1–13 ms、只占远程 broker 全程时延约 10%；明文本地基线 3.7 ms；ESP8266 约 120 ms；某公网 broker 48 小时约 140 万条 `iot/` 前缀消息（前缀碰撞的论据）。
**动手实现**：
- topic 混淆用 **B/C 方案的 PRF 同步 + DHKE**（两客户端）或预共享密钥 + AES（多方），**每种消息类型独立 PRF/盐**；
- 随机 topic **各层级等长**（hash + 占位符补齐），防止按长度分类；用 `#` 通配符订阅 `p/#` 前缀空间过滤无关消息；
- 若采用链式换题（A 方案），**必须配 QoS 1/2**（对应任务 3 的 QoS 支持），否则丢一条消息整条链断裂；中途加入的节点走预定义 topic 的映射请求机制；
- 映射表**按消息频率排序**（接收端可在线统计建序），把解混淆的试错开销摊到最低；
- broker 侧零改动、全兼容 MQTT 3.1 标准——毕设实现可直接复用任意 Mosquitto 部署验证；参考开源实现 github.com/mafmcfly/aotp-mqtt；
- 边缘网关定位：解混淆放在无约束设备上几乎免费（RPi 1–13 ms，仅占远程传输 10%；ESP8266 却要 120 ms）——网关是天然的解混淆/密钥材料托管点：MCU 端只采集发布，网关端做 topic 混淆与解混淆，安全功能与算力约束按层分配。
**测试**：
- 可模仿的实验设计：混淆 vs 明文 × 本地 vs 远程 broker 的 2×2 对照；每 10 分钟一轮、连续 4 天的长时程采样抹平 broker 负载波动（每种组合 3800+ 次）；
- 时延口径：「发布时刻 → 接收端解混淆完成可用时刻」（payload 带发布时间戳），收发同机免除时钟同步问题；报告 CDF/分位数而非只报均值；
- 逐 topic 的解混淆耗时分布（39 个 topic 池）可定位试错开销的结构性差异；注意本文未量化消息体积、订阅流量与内存占用，毕设若实现需补测。

## 怎么用 & 怎么做（研0 版落地清单）

> 思维导图：[[12思维导图.canvas]] · 总览：[[毕设论文总导图.canvas]]

**什么时候翻这篇**：写「安全与展望」章时（topic 元数据泄露面 + 五种混淆策略）；想做隐私扩展实验时（2×2 对照设计现成）；部署公网/跨网 broker 担心 topic 画像时。

**在 Ubuntu 22.04 上**：
- 2×2 对照复现（p.4）：本地 `mosquitto`（loopback 基线 ≈3.7 ms）与远程 broker 各跑「明文 / AOTP 混淆」两组，每 10 分钟一轮、连续 1–4 天——长时程采样抹平负载波动。
- 混淆原型最省路径：先跑论文开源实现（github.com/mafmcfly/aotp-mqtt，Python + Paho）验证流程，再用 C++ 重写热路径。

**在树莓派上**：
- 网关分工按算力分层（p.5 关键结论）：树莓派网关做 topic 混淆/解混淆（实测 1–13 ms、占远程时延约 10%，可接受）；MCU 端（ESP8266 类）只采集与发布（它做解混淆要 120 ms）。

**C++ 实现要点**：
- hash 链核心用 OpenSSL：`HMAC(EVP_sha256(), ...)` 做 PRF；AOTP 的隔项掺盐递推按 p.4 公式 `H^i = F(H^{i-1} · P(i))`，发送端存起始串 `s`、前缀 `p` 与各链长 `n_t`，每发布一条消耗一环。
- 随机 topic 各层级等长（hash + 占位符补齐），防按长度分类（p.3）；映射表按发布频率排序，高频 topic 排前面试——解混淆是试错法，排序直接决定耗时（p.5）。
- 若采用方案 A（链式换题）必须配 QoS 1/2：丢一条消息整条 topic 链就断（p.2）——与任务 3 的 QoS 模块联动。
