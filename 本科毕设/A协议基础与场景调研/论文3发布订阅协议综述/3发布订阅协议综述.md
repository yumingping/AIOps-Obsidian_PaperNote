## 一、abstract/introduction（p.1–2）
### 痛点 / 已有方法为什么不行
- **IoT 协议 hundreds of choices**：与 Web 领域 HTTP（上网浏览网页用的协议）一统不同，IoT（Internet of Things，物联网：给普通设备装上联网与数据交换能力）有数百种协议各管一段（p.1）。request/response（请求-响应模式：像打电话一问一答，问完必须等对方答完才能问下一句）协议同步、非事件驱动，在 M2M（machine-to-machine，机器对机器：设备之间不经人直接对话）场景很快到达极限；[[发布订阅模式]]（发布方把消息发到一个「频道」，订阅了该频道的接收方自动收到，类似微信公众号：作者发文、关注者自动收到，双方互不认识也能对上）以异步、事件驱动、时间/空间/同步三重解耦成为更合适的选择，催生了 1:n、m:1、m:n 灵活通信（p.1）。
- **IoT → [[IIoT（工业物联网）]]（Industrial Internet of Things：物联网用在工厂、电网、机床等工业场景的子集——好比把家用智能灯泡换成生产线传感器，掉线一次就可能是真金白银的损失）的需求跃迁**：工业 4.0（Industry 4.0，德国提出的制造业智能化升级浪潮）使这些协议进入工业环境，除了 IoT 已知的能耗、安全、可扩展、[[互操作性（interoperability）]]（不同厂家、不同系统的设备不仅能互传数据，还能正确理解和使用这些数据，好比不同品牌电器要插头、电压、频率全对上才能真正通电）要求外，还按业务关键性新增**实时能力（real-time capability）与高可靠性**要求——**在 IoT 里已验证可用的协议，未必满足 IIoT 要求**（p.1）。
- **已有综述覆盖不足**：现有调研多局限于特定应用领域（智能电网、机器人、无线通信），且**大多未（完整）纳入工业场景的特定需求**（p.1–2）：如 [32] 评估 [[MQTT（消息队列遥测传输）]]（MQTT：极轻量的消息传输协议，设备把消息发给中转站 broker、订阅者从 broker 取，类似快递驿站收发件）、CoAP（给内存和带宽都极有限的小设备用的简化版网页协议）、AMQP（功能更全但更重的企业级消息协议，银行/电信常用）、HTTP 但漏掉 scalability 与 real-time capability，且只覆盖少量协议；[8] 只看实时与可扩展两维（p.2）。

### 新方法（一段话）
本文限定研究对象为**实现 publish/subscribe 模式的协议**（原生支持或通过标准扩展支持均可），先从文献中提炼工业领域的五条关键需求（Req-1 互操作、Req-2 安全、Req-3 可扩展、Req-4 实时、Req-5 可靠），再逐协议对照评估，找规范局限、导出开放研究问题（p.2）。评估对象 8 个：MQTT、CoAP、AMQP、XMPP（源自聊天软件的可扩展通信协议）、MQTT-SN（给无线传感器网络用的更精简 MQTT 变体）、[[OPC UA（OPC Unified Architecture）]]（工业自动化的「通用语言」标准：不只传数据，还规定数据的含义与安全规则）、DDS（高可靠低时延的军用/航空级数据分发协议）、DPWS（让小设备用网页服务方式互通的协议）。

### 本文贡献（p.2）
1. 基于文献的工业领域**需求定义**（五条 Req）。
2. IIoT 协议栈逐层描述（应用/传输/网络/网络接口，p.2–3）。
3. 8 个 publish/subscribe 协议的**特性描述与五需求评估**（p.3–7）。
4. 协议规范的局限与开放研究问题（p.7）。

## 二、需求定义（Section 2, p.2）
IIoT 是 IoT 子集，两者共同要求互操作、安全、设备数可扩展；但 IoT 设备常电池供电、无线连接、数据量低到中、**允许丢包**，IIoT 则数据量与数据关键性都高，**常要求高可靠、实时、低时延**（p.2）。五条需求的两点式定义：

1. **互操作（Req-1）**：**含义**——两个以上系统交换信息并使用所交换信息的能力（IEEE 定义），细分为 technical（协议标准化）、syntactical（统一数据格式）、semantic（统一数据/信息模型）三层；**为什么需要**——只保证能传数据不够，必须三层齐备才算完全满足（p.2）。
2. **安全（Req-2）**：**含义**——跨所有通信层的整体属性；本文只看应用层与传输层，最低要求是 [[TCP（传输控制协议）]]（Transmission Control Protocol：可靠传输协议，像挂号信——每封编号、对方签收才算送到、丢了补寄，代价是慢一点）场景指定 TLS（Transport Layer Security：给网络通信加的一层加密，像把明信片装进密封信封）、[[UDP（用户数据报协议）]]（User Datagram Protocol：不保证送达的快速传输协议，像广播喊话——喊出去就算完成，没人确认）场景指定 DTLS（给 UDP 用的 TLS 加密版）；**为什么需要**——否则必须在应用层补安全机制（p.2）。
3. **可扩展（Req-3）**：**含义**——管理增长设备数及其信息的能力，双维度：网络可扩展（数百至数千设备）+ 数据量可扩展（数 MB 量级）；**为什么需要**——两个维度都要达标才算完全满足（p.2）。
4. **实时（Req-4）**：**含义**——在精确定义的时限内确定性（deterministic）传输消息，服务 mission/safety-critical 应用；要求应用层协议与其依赖的传输层协议都满足；**为什么需要**——下层不实时则上层单方面实时无意义（p.2）。
5. **可靠（Req-5）**：**含义**——保证包成功送达、顺序正确、去重；**为什么需要**——需要可靠传输协议（TCP）打底；**最高可靠性 = 传输层 + 应用层双重可靠**，仅 TCP 不足以完全满足（p.2）。

## 三、IIoT 协议栈（Section 3, p.2–3）
### 协议栈全貌（Figure 1, p.3，未提取）
四层结构（原文 Figure 1 为矢量图，图源目录无图，此处文字转述）：
- **应用层**：MQTT、CoAP、AMQP、XMPP、MQTT-SN、OPC UA、DDS、DPWS（即全部被评估协议）；
- **传输层**：TCP（配 TLS）、UDP（配 DTLS）、QUIC（基于 UDP 重造的新一代传输协议：补上流控、低时延建连、路径迁移、安全、丢包检测与拥塞控制，RFC 9000——兼取 UDP 的快与 TCP 的可靠，像把挂号信流程简化重造的「快速挂号信」）；
- **网络层**：IPv4 / IPv6；
- **网络接口**：IEEE 802.3（Ethernet）、IEEE 802.11（Wi-Fi）、5G。

### 应用层：两种架构（p.3）
- **broker-based（集中式）**：[[Broker（消息代理）]]（broker：居中转发的服务器，像快递驿站——所有包裹先到驿站再分发，收发双方不用见面）维护与 publisher（发布者：发消息的一方）、subscriber（订阅者：收消息的一方）的直接连接，代表双方转发消息；**代价 = broker 是[[单点故障（SPOF）]]（single point of failure：一个部件坏了整套系统停摆，像全班作业只交一个课代表，课代表请假全班停交）**（p.3）。
- **broker-less（去中心式）**：无中心实例故无 SPOF，更高效可扩展，消息分发通常靠 **(IP) [[组播（multicast）]]**（一份数据同时发给一组接收者，像班级群里发一条通知全班可见，不用挨个私聊）（p.3）。
- 作者刻意提醒**不要迷信 pub/sub**：HTTP 的阻塞行为并不降低效率、实现更简单，且请求可由客户端发起（订阅方做不到）——好反例（p.3）。

### 传输层（p.3）
- **含义**：UDP 简单、无可靠性与流控/拥塞控制；TCP 靠序列号、ACK、校验和保证传输/顺序/去重，另有流控与拥塞控制；QUIC 试图兼取两者。
- **关键判断**：**TCP/QUIC 满足 Req-5（可靠传输）但因流控/拥塞控制机制的不可预测行为而不满足 Req-4（实时）**；**UDP 协议潜在实时可达**，前提是底层与应用层补实时机制。作者注明此判断仅针对标准描述的机制本身，不否定改造后实时化的可能（p.3）。

### 网络接口（p.3）
工业高要求场景**有线优先**，趋势是从专有总线/Industrial Ethernet 转向标准 Ethernet 之上的开放标准 **TSN（Time Sensitive Networking，时间敏感网络：给以太网装上「准点保证」，让数据包按约定时刻到达，像给公交车划定专用道和时刻表）与 SDN**（软件定义网络：把网络的「指挥权」集中到软件统一调度），且概念已进入 5G 与 Wi-Fi（802.11ax）；本文评估传输/应用层实时性时**假设底层技术实时可用**（p.3）。

**图解**（Figure 1, p.3，未提取，以上为文字转述）：这张图把 IIoT 通信画成一栋四层楼，每层只与上下层打交道。怎么看：从上往下——最顶层是应用层（8 个被评估协议都在这一层，是论文要打分的对象）；往下依次是传输层（TCP/UDP/QUIC，决定「可靠但可能慢」还是「快但不保证送到」）、网络层（IPv4/IPv6，负责寻址）、网络接口层（Ethernet/Wi-Fi/5G，物理上怎么传）。纵向的搭接关系表示上层协议必须选某种传输层落地——这正是全文核心结论的来源：**应用层的可靠/实时与否，被它选的传输层决定了一大半**。读图结论：协议不能孤立评价，必须看整个协议栈的组合。与毕设的关系：毕设架构图（任务2）可直接照搬这套分层画法（应用层 MQTT / 传输层 TCP(TLS) / 网络层 IP / 接口层 Ethernet·Wi-Fi·5G），逐层做选型论证。

## 四、协议逐个评估（Section 4, p.3–7）
文献覆盖度（Table 1, p.4，文字转述）：15 篇综述中各协议出现次数——**MQTT 14、CoAP 12、DDS 11**、AMQP 7、XMPP 6、OPC UA 5、MQTT-SN 4、DPWS 2。工业侧协议中 DDS 的文献关注度显著高于 OPC UA（p.3–4）。

### MQTT（4.1, p.4）
**含义**：OASIS 标准（3.1.1 与 5.0 两版），broker-based 轻量 M2M 协议；**data-agnostic**——不定义数据格式与建模能力。
- Req-1 **部分满足**（无数据建模，需按用例自定义）（p.4）；
- Req-2 **满足**：TCP+TLS，标准还定义用户/设备认证、资源访问授权、控制包完整性与隐私（p.4）；
- Req-3 **满足**：设备数上多 broker 实现可支撑数千并发，HiveMQ 借 clustering 验证到 **百万级设备**；payload 上限 **256 MB**（p.4）；
- Req-4 **不满足**：**基于 TCP**（低复杂度 + 二进制编码使其自身轻量、潜在实时，但传输层拖累）（p.4）；
- Req-5 **满足**：**[[QoS（服务质量）]]（Quality of Service：消息送达的「保险等级」，等级越高越不丢但越慢）0（at most once，至多一次）/ 1（at least once，至少一次）/ 2（exactly once，恰好一次）三级 + TCP**（p.4）。

### CoAP（4.2, p.4）
**含义**：RFC 7252，面向资源受限环境的轻量 RESTful 协议；基础标准是 request/response，**pub/sub 靠标准扩展**——Observe 扩展（RFC 7641）提供 broker-less 资源观察，另有 draft 状态的 broker-based 扩展。
- Req-1 部分：全 RFC 化保证 technical 互操作；SenML+JSON/CBOR/XML/EXI 提供数据格式，但**传感器公共数据模型远不如 OPC UA 成熟**（p.4）；
- Req-2 满足：UDP+DTLS，另有应用层 OSCORE 与 ACE（p.4）；
- Req-3 满足：低复杂度可扩展设备数；**block-wise transfer**（RFC 7959）解决 UDP 上传大数据（p.4）；
- Req-4 部分：UDP 底子潜在实时，但需**应用层 TDMA（时分多址：把时间切成小格子，每台设备按分配到的格子发言，像课堂按座位顺序轮流发言）时隙机制**（[23–25] 已示范），且要同步应用到 pub/sub 扩展上（p.4）；
- Req-5 部分：可靠性层用 message ID + CON/NON 消息保证送达、去重、排序（p.4）。

### AMQP（4.3, p.5）
**含义**：OASIS 标准，轻量 M2M 协议，同时支持 request/response 与 pub/sub；二进制编码 + XML/JSON + 自有类型系统。
- Req-1 部分：类型系统**不如 OPC UA 强大**，需扩展（p.5）；
- Req-2 满足：TCP+TLS+**SASL**（应用层加密与认证）（p.5）；
- Req-3 满足：设备数可用 clustering 扩展并**借 clustering 消除 broker SPOF**；消息大小上限实际由 broker 实现决定（p.5）；
- Req-4 不满足：基于 TCP（p.5）；
- Req-5 满足：TCP + **at-least-once** 传输保证（p.5）。

### XMPP（4.4, p.5）
**含义**：RFC 6120，源自**即时消息**而非 M2M，基于 client/server 架构交换 XML；核心规范只定义 request/response，pub/sub 靠 **XEP-0060** 扩展。
- Req-1 部分：无自有数据建模，仅保证 technical + syntactical 两层（p.5）；
- Req-2 满足：TLS（RFC 7590）+ SASL + 端到端签名/对象加密（RFC 3923）（p.5）；
- Req-3 满足：去中心（联邦）架构利于设备数扩展；大数据量可用 in-band bytestream（XEP-0047）分块（p.5）；
- Req-4 **不满足**：XML 解析开销与高复杂度导致性能低，时间关键应用不可能（p.5）；
- Req-5 部分：除 TCP 外**规范不提供任何应用层送达保证机制**（p.5）。

### MQTT-SN（4.5, p.5）
**含义**：面向无线传感器网络的极轻量 MQTT 变体，IBM 发布 v1.2 规范，OASIS 标准化进行中；对底层传输/网络技术 agnostic，但**必须经 gateway 接入 MQTT broker**——gateway 可为 standalone 或集成在 broker 内。
- **关键机制**：gateway 分 **transparent（每设备一条连接）与 aggregating（全部设备共用一条连接）**两种；transparent 更易实现但**扩展性更差**（设备多 = 并行 TCP 连接多）（p.5）；
- Req-1 部分（data-agnostic）；Req-2 **部分**：多基于 UDP/IP 可用 DTLS，但**现行规范缺安全指南与补充机制**（标准化中应会补）（p.5）；
- Req-3 部分：**standalone gateway 本身是新的 SPOF**；payload 上限 65,535 octets 且**不支持分片重组**，实际受底层技术限制（p.5）；
- Req-4 部分：极轻量 + UDP 潜在实时，仍需 TDMA 类时隙补充（p.5）；
- Req-5 部分：QoS 同 MQTT 三级，另有**第四级 QoS——无需建连直接发布、对送达无任何保证**（p.5）。

### OPC UA（4.6, p.5–6）
**含义**：IEC 62541 标准系列（20+ 部分），OPC Foundation 驱动，定义可互操作、安全的通信架构。Part 1 是 client/server 的 request/response + 基于 subscribe/notify 的基础 pub/sub；**Part 14 扩展出 broker-less（OPC UA UDP / OPC UA Ethernet，UADP 编码 + multicast 组分发）与 broker-based（指定 AMQP、MQTT 为传输绑定）两种 pub/sub 传输**。
- Req-1 **唯一完全满足**：**极强且可按组织/厂商扩展的数据与信息模型**，在全部被评估协议中独一无二（p.6）；
- Req-2 部分：整体安全机制丰富（Part 2 认证/授权/加密，Part 18 基于角色的安全；德国 BSI 评定基础安全），**但 Part 14 的 multicast 使 DTLS 不可用 → 传输层安全缺失**，只能靠 Part 2 的应用层端到端签名/加密——**安全是该路线的开放研究问题**（p.6）；
- Req-3 部分：multicast 无 SPOF、设备数扩展性理论好但**缺实践调研**；UDP+multicast 限制 Internet 范围通信与数据量扩展（p.6）；
- Req-4 **满足**：实时性已在 open62541 参考实现 + TSN 上示范；**经 OPC UA 配置 TSN 是有前景的方向**（p.6）；
- Req-5 部分：OPC UA UDP **不保证及时性、送达、排序、去重**，但有序列号与重传机制补偿（p.6）。

### DDS（4.7, p.6）
**含义**：OMG 标准；基础标准只定义 pub/sub 模型（API），互操作靠**DDSI-RTPS 线上协议**——基于 UDP + IP multicast。
- Req-1 部分：自有 XML 类型系统保证 syntactical，**semantic 与组织级互操作不及 OPC UA**（p.6）；
- Req-2 部分：UDP multicast 使 DTLS 不可用；有专门安全规范以**应用层插件**形式提供认证、授权、加密、签名、日志、数据打标（p.6）；
- Req-3 部分：mission-critical 场景低时延、极高可靠、去中心架构设备数高度可扩展，**但 multicast 是点对点场景与 Internet 范围部署的扩展性障碍**；数据量受 UDP 限制，有分片机制补偿；同样缺实践评估（p.6）；
- Req-4 **满足**：DDSI-RTPS 生而实时（UDP+multicast）；**DDS-TSN 正由 OMG 标准化**（p.6）；
- Req-5 部分：定义可靠/不可靠两种传输，可靠模式保证送达与顺序（p.6）。

### DPWS（4.8, p.6–7）
**含义**：OASIS 标准，实现 SOA 范式的 M2M 协议，用 web services 让资源受限设备互通；pub/sub 通过**类似 CoAP Observe 的 broker-less eventing（subscribe/notify）**实现；医疗领域发展为 **MDPWS（IEEE 11073 系列）**。用 SOAP 交换 XML。
- Req-1 部分：无数据建模能力，仅 technical + syntactical（p.6）；
- Req-2 满足：TLS、消息签名、认证（p.6–7）；
- Req-3 **不满足**：eventing 机制有设备扩展性问题；**SOAP envelope 上限 32,767 octets**（p.7）；
- Req-4 不满足（Table 2 记 ✗）：协议自身潜在实时（MDPWS+TSN 已在医疗域示范），但**默认传输是 TCP**，文献 [46] 指出传输层也需换实时协议（如 UDP）（p.7）；
- Req-5 部分：仅靠 TCP 保证，应用层无补充机制（p.7）。
- **原文疑误**：p.7 正文此段以 "Therefore, Req-3 is not fulfilled." 收尾，但上下文讨论的是实时能力，且 Table 2 中 DPWS 的 Scalability 记 ⋄、Real-time 记 ✗——**疑为 Req-4 之笔误**，如实记录。

## 五、评估汇总与结论（Table 2 + Section 5, p.7）
Table 2（p.7，原文为表格，此处按提取文本完整转述；✓=满足，⋄=部分满足/可经扩展满足，✗=不满足）：

| 需求 | MQTT | CoAP | AMQP | XMPP | MQTT-SN | OPC UA | DDS | DPWS |
|---|---|---|---|---|---|---|---|---|
| Interoperability | ⋄ | ⋄ | ⋄ | ⋄ | ⋄ | ✓ | ⋄ | ⋄ |
| Security | ✓ | ✓ | ✓ | ✓ | ⋄ | ⋄ | ⋄ | ✓ |
| Scalability | ✓ | ✓ | ✓ | ✓ | ⋄ | ⋄ | ⋄ | ⋄ |
| Real-time capability | ✗ | ⋄ | ✗ | ✗ | ⋄ | ✓ | ✓ | ✗ |
| Reliability | ✓ | ⋄ | ✓ | ⋄ | ⋄ | ⋄ | ⋄ | ⋄ |

**核心结论**：
- **没有任何一个被评估协议能完全满足全部五条需求**，且这与预期一致——需求间普遍存在 trade-off（p.7）。
- **需求的满足度与传输机制的选择深度绑定**：TCP 保可靠但不实时；UDP 潜在实时但必须在应用层自建可靠性；**只有 OPC UA 与 DDS 生而面向实时，但都因 multicast 而缺传输层安全、数据量扩展受限**（p.7）。
- **OPC UA 的数据建模使其成为唯一完全满足三层互操作的协议**（p.7）。

开放研究问题（p.7）：给 MQTT-SN、CoAP 补实时机制并研究其与 TSN/SDN 的协同；把其他协议集成进 OPC UA（标准已规定 MQTT、AMQP 绑定）；**multicast 类协议（OPC UA、DDS）严重缺真实场景的实践性能评估**；需按 throughput、RTT、latency 等参数补性能评估；**QUIC 集成**——有前景但现行协议规范均未纳入。

## 对毕设的帮助

**写论文**
- 调研章节（对应任务1）直接采用本文「先定义需求、再逐协议打分」的五需求矩阵（Req-1 互操作 / Req-2 安全 / Req-3 可扩展 / Req-4 实时 / Req-5 可靠，p.2）作为评估框架；引用 Table 2（p.7）的 ✓/⋄/✗ 结论论证为什么选 MQTT 作边缘消息中间件的基础协议（安全/可扩展/可靠满足、生态与文献覆盖最广），并如实声明其 Req-4 不满足的边界条件。
- 可直接引用的数字：15 篇综述中 MQTT 出现 14 次（p.3–4）；HiveMQ 借 clustering 验证到**百万级设备**、payload 上限 **256 MB**（p.4）；**OPC UA 是唯一完全满足三层互操作的协议**（p.7）。
- 相关工作引用 p.7 原句「multicast 类协议严重缺真实场景的实践性能评估，需按 throughput、RTT、latency 补性能评估」论证毕设性能测试的必要性；「QUIC 集成」尚未被任何现行协议规范纳入（p.7），可写进展望。

**动手实现**
- 总体架构（任务2）：仿照其协议栈分层画法（Figure 1, p.3，未提取），把端—边—云消息流转画成「应用层 MQTT / 传输层 TCP(TLS) / 网络层 IP / 接口层 Ethernet·Wi-Fi·5G」分层图。
- 传输层选型按其关键判断（p.3）：TCP 保可靠但不实时、UDP 潜在实时但须应用层自建可靠性——毕设默认 TCP+TLS，接受时延代价换可靠性，并在论文中明确该取舍。
- 涉及资源受限设备时参考 MQTT-SN gateway 的 transparent vs aggregating 之辨（p.5）：aggregating 连接数少扩展好，但网关是 SPOF——架构图中标注单点并给降级策略。
- broker SPOF 教训（p.3）支持在边缘节点间做 broker 冗余/桥接；「最高可靠性 = 传输层 + 应用层双重可靠」（p.2）正对应毕设 QoS 1/2 + TCP 组合（任务4）。

**测试**
- 基准测试（任务6）指标按其点名口径取：throughput（吞吐）、RTT（往返时延）、latency（时延）（p.7）。
- 借鉴「先定义需求、再打分」的方法论，把毕设自研中间件与 Mosquitto 等现成 broker 放进同一张需求/性能对照表，使评测结论可比。
- 其指出的「multicast 类协议缺实践评估」提示：若展望涉及 OPC UA/DDS 类方案，应补真实场景测试而非只引标准声明。

## 怎么用 & 怎么做（研0 版落地清单）

> 思维导图：[[3思维导图.canvas]] · 总览：[[毕设论文总导图.canvas]]

**什么时候翻这篇**：制作毕设「协议对比表」与选型论证时（五需求矩阵是现成框架）；架构图定稿前自查「单点与取舍有没有标注」时。

**在 Ubuntu 22.04 上**：
- 本文是规范级综述，无可复现实验；它的评估动作要落在毕设自己的对比表里：把自研中间件与 Mosquitto 放进同一张「需求 × 满足度」表（互操作/安全/可扩展/实时/可靠，✓/⋄/✗ 三档），评测方法学由此而来。
- 想体验「UDP 潜在实时但可靠性自建」（p.3）：`sudo apt install netcat-openbsd` 后用 `nc -u` 收发 1000 条小消息，与 `mosquitto_pub -q 2` 对比时延与丢失——直观感受传输层取舍。

**在树莓派上**：
- 若扩展到真受限设备（MCU/无线传感节点），参考 MQTT-SN gateway 的 aggregating 模式：树莓派网关聚合全部传感器流量、共用一条 MQTT 连接上云——连接数少、扩展好，但要在架构图上标注网关本身是单点（p.5）。

**C++ 实现要点**：
- 按 p.3 的协议栈分层定实现顺序：先明确「应用层 MQTT / 传输层 TCP(TLS) / 网络层 IP / 接口层 Ethernet·Wi-Fi」边界；TLS 用 OpenSSL（`SSL_connect/SSL_read/SSL_write` 包一层抽象，将来换 QUIC/UDP 不动上层）。
- 把「最高可靠性 = 传输层 + 应用层双重可靠」（p.2）落成代码事实：TCP 保序之外，应用层 QoS 1/2 各自维护 PUBACK/PUBREC 确认状态机。
