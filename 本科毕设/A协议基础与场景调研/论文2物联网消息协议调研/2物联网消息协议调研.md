## 一、abstract/introduction（p.1–2）
### 痛点 / 已有方法为什么不行
- IoT 设备算力/存储受限，选一个**轻量、可靠、可扩展、可互操作、可扩展、安全**的消息协议非常困难；现实是**一个 IoT 系统往往同时用多种协议**来支撑设备异构性（p.1）。
- 报文开销差两个数量级：**HTTP**（[[HTTP（超文本传输协议）]]：浏览器访问网页用的协议，报文头像又大又正式的「挂号信信封」）未压缩请求头 200 B–2 KB（常见带 user-agent 的约 700–800 B），而 **MQTT**（[[MQTT（消息队列遥测传输）]]：为小设备和差网络设计的超轻量消息协议，报文像「明信片」一样极小）最小包仅 2 字节；温度传感器用 HTTP 传一天数据可能中途就没电（p.2）。
- 应用层协议能力超过物理层实际速率只会堆高时延——选协议必须考虑底层链路（如 IEEE 802.15.4（低功耗无线通信的物理层标准，ZigBee 的底座）物理层 250 Kbps、包长约 127 B）（p.1–2）。
- 已有综述要么只看 data link 层（[120]–[129]），要么只看应用层，**缺少把 OSI（国际通用的网络分层模型：把通信从物理线路到应用软件分成七层，便于逐层讨论）各层协议串起来的研究**（p.2）。

### 新方法（一段话）
按两条硬证据选定六种应用层协议——**HTTP(S)、CoAP（[[CoAP（受限应用协议）]]：给算力弱、电池小的设备用的「迷你版 HTTP」，报文头仅 4 字节）、MQTT、AMQP（[[AMQP（高级消息队列协议）]]：企业级消息协议，像带智能分拣台的邮局，功能全但偏重）、XMPP（源自即时通讯软件的文本协议，IM 起家）、DDS（[[DDS（数据分发服务）]]：无中心服务器的实时数据分发标准）**：一是 Eclipse Foundation 2015–2019 年 IoT 开发者调查的采用率，二是主流 IoT 云平台的协议支持度（p.6–7）。对每个协议讲机制，再用九个维度（互操作、服务供给、微服务（把大系统拆成许多可独立部署升级的小服务）与分布式追踪、可扩展性、性能、可靠性、安全、适应性/扩展性、实现与采用率）横向比较，最后逐协议列优缺点（p.2, 17）。

## 二、related work（p.2–4）
- Thangavel 等 [4]：MQTT 在低丢包率下时延低于 CoAP；**高丢包率下 MQTT 反而劣化**；消息小且丢包率 ≤25% 时 CoAP 流量开销远小于 MQTT（p.3）。
- Tandale 等 [5]（树莓派 3 作网关，4G 与宽带两种网络）：**CoAP 对小 payload（一条消息里真正装的数据，相当于「信纸」；协议头是「信封」）更高效，payload 增大后性能恶化**（p.3）。
- Thota & Kim [6]：MQTT 与 CoAP 都能 100% 传输（少量人为丢包下），重传都较高效；CoAP 在小数据量下丢包率更低（p.3）。
- 结论性空白：需要一份**结合具体 IoT 用例、覆盖互操作/可扩展/性能/安全/可靠性**的应用层协议对比（p.4）。

## 三、IoT 参考模型与协议选型（p.4–8）
### A. 云架构 vs 边缘架构（p.4）
传统 IoT 云架构把全部数据搬上云做存储与聚合；**edge-based 架构只把部分数据上云，数据积累与抽象部分下沉到边缘**——这正是[[云边端协同]]（端、边、云三层算力分工配合）的部署形态，设备越多省的流量越多——所以**选部署架构和选消息协议必须一起定**（p.4）。

### B. CIoT 参考模型与各层技术（p.4–5）
- Communication-centric IoT（CIoT）参考模型分层：physical / data link / network / transport / application（Fig.1, p.4，未提取）。
- Data link 层典型技术：Z-Wave（智能家居）、Weightless-N/W/P（三种 LPWAN（Low-Power Wide-Area Network，低功耗广域网：传得远、省电但速率低）各自面向传感网络/TVWS/双向工业监测）、Sigfox（订阅制 LPWAN）、**LoRaWAN**（低成本双向远距、百万级节点）、**ZigBee**（基于 IEEE 802.15.4，星/簇树/mesh 拓扑，**单网最多 65,000 节点**，低速率）（p.4）。Table 1（数据链路层协议对比表）内容提取缺失（p.5，未提取）。
- Network/Transport 层：**6LoWPAN** 让 IPv6 包跑在低功耗受限设备上；大量地理分散的受限设备用 **UDP**（无连接的传输层协议：发出去就不管对方收没收到，省开销）优于 **TCP**（先建连接、保证按序送达的传输层协议：可靠，但建连和维护都有开销）（p.5）。
- Application 层：本文六协议 + 工业协议 Modbus、DNP3、OPC、MMS（p.5）。IoT 应用距离需求汇总表 Table 2 内容提取缺失（p.5，未提取）。

### C. 四种通信类型：协议选型的第一判据（p.6）
D2D（设备直连）、D2A（设备—应用）、D2G（设备—就近网关）、D2C（设备—云）。**并非所有协议都支持全部类型：MQTT 是 D2C 型，CoAP 只支持 D2D**（p.6）。设备没有直连能力（如 RFID 标签）就必须经网关转 D2G/D2C（p.6）。

### D. 选型策略与云平台支持（p.6–8）
- 协议入选依据：文献综述 + **Eclipse Foundation 2015–2019 开发者调查采用率**（p.6–7）。
- **10 个主流 IoT 云平台全部支持 HTTP(S) 与 MQTT**；AMQP 6 家、CoAP 4 家；**没有一家支持 DDS**（Table 3, p.7）。Oracle IoT 与 Siemens MindSphere 覆盖全部五种协议（Fig.4, p.7）。Table 3 的逐平台明细提取缺失（p.7，未提取）。
- 平台本身也是设计变量：异构性高的应用选支持协议多的平台；此外还有成本、带宽、可靠性、安全等因素（p.8）。

## 四、六协议逐个精读（p.8–14）
### A. HTTP（p.8）
应用层无状态 request-response（一问一答：客户端发请求、服务器回响应，像柜台办事）协议；内容协商（content negotiation）使其能服务异构设备；主流版本仍是 1.1（p.8）。

### B. CoAP（p.8–9）
- **含义**：面向受限设备（8 位 MCU（Microcontroller Unit，微控制器：家电里那种便宜的单芯片小电脑）+ 小内存）的 web 传输协议，REST 风格（URI + 媒体类型；REST：把一切当「网址可寻址的资源」，用 GET/PUT/POST/DELETE 等统一动作读写，网页 API 的主流风格），跑在 **UDP** 上（`coap`），安全用 **DTLS**（`coaps`；TLS 的 UDP 版——TLS 即网页 https 用的加密技术，DTLS 把类似加密搬到 UDP 上）（p.8）。
- **最小二进制头 4 字节**；CRUD 操作映射 HTTP 方法，状态码类 HTTP（2 成功 / 4 客户端错 / 5 服务端错）（p.8–9）。
- 四种消息类型（Table 5, p.9）：**CON（confirmable）会被重传直到收到 ACK，ACK 携带与 CON 相同的 message id**——这就是 CoAP 在 UDP 上的可靠送达机制（p.9）。Observe 扩展支持资源状态变化的观察/通知（p.9）。
- *Fig.6–8（DTLS 分层、报文结构、CON/ACK 流程，p.8–9）：图源目录中有对应提取图，此处未选用；要点已如上文字记录。*

### C. MQTT（p.9–11）
- **含义**：OASIS（国际结构化信息标准组织，MQTT/AMQP 等标准都出自它）标准的**发布/订阅轻量协议，专为不可靠网络与间歇连接设计**（[[发布订阅模式]]：发送方只管「按主题发」、接收方只管「按主题订」，双方互不认识、靠中间设施解耦——像报社与订户），跑在 TCP/IP 上（Fig.9, p.10）；面向 M2M（Machine-to-Machine，设备与设备/服务器间的机器间通信），近实时（p.9–10）。
- **broker 模型**：broker（[[Broker（消息代理）]]：消息中转站，收发双方都只跟它打交道，像小区快递柜）居中，publisher 经 broker 发消息、subscriber 按 topic 订阅；**一次 publish 即可扇出到所有订阅者**；实现有 Mosquitto、eMQTT、HiveMQ、Moquette 等（p.10）。

![[2-Fig1_p10.png]]
*图 Fig.10（p.10）：MQTT 集中式 broker 模型——温度计 publish "/temp"、灯 publish "/status"，订阅 "/temp" 的客户端各收到 23 ℃，broker 完成全部过滤与分发。*

**图解**：图中央云形大圆是 MQTT Broker，四周客户端都与它相连。左上温度计沿绿色箭头 publish topic "/temp"（消息气泡写着 23 ℃），左下灯泡 publish topic "/status"（气泡写着 true）；右侧两台电脑各自沿红色虚线 subscribe（订阅）——右上那台订了 "/temp"，右下那台同时订了 "/temp" 和 "/status"。broker 收到消息后按主题匹配，沿绿色箭头把 23 ℃ 推给两个订阅者、把 true 推给右下订阅者。读图结论：**收发双方只面对 broker，互不知道对方存在；一次发布即可扇出全部订阅者**——但反向看，所有压力也集中在 broker 上（呼应 §六.D 的 SPoF 与扇出模型）。与毕设的关系：这张图就是毕设要实现的 broker 核心行为——按 topic 匹配、一次发布扇出全部订阅者。

- **连接/订阅/发布流程**（Fig.12, p.10）：CONNECT → CONNACK → SUBSCRIBE → SUBACK → PUBLISH →（订阅端确认 PUBCREC）（p.10）。
- **QoS 0/1/2**（[[QoS（服务质量）]]：broker 对「这消息保证送到什么程度」的三档承诺——QoS 0 等于寄普通信件，丢了不赔、只发一次；QoS 1 等于挂号信，没收到回执就反复寄，可能重复投递；QoS 2 是对账式流程，确保恰好一次，最稳也最费事）（Table 6, p.10–11）：QoS 级别在 Connect Flags 的 Will QoS 位（bits 4/3）指定——Will 指[[遗嘱消息]]：设备异常掉线时由 broker 代发的「告别通知」，遗嘱本身也有 QoS 等级；**级别越高送达越可靠，但 broker 保障开销越大**——QoS 2 且订阅者多的场景对 broker 开销最重（p.10–11）。各云平台对 QoS 2 的支持参差（Table 7, p.11，内容提取缺失）。
- **安全隐患**：MQTT 允许端点自行决定是否校验 UTF-8 字符串（如 topic 名），恶意客户端可用含非法 Unicode 码点的 topic 使订阅端断连，配合 retain + QoS 2 可造成 **DoS**（Denial of Service，拒绝服务攻击：把对方骚扰到无法正常提供服务）（p.11）。

### D. AMQP（p.11–13）
- **含义**：OASIS + ISO 双标准的二进制消息协议，为企业环境与 MOM 互操作而生；同时支持 request-response 与 publish-subscribe，支持灵活路由与事务（p.11）。
- **消息分发三组件：exchange → binding → queue**（[[Exchange 与 Binding（交换器与绑定）]]：exchange 是「分拣台」、binding 是「分拣规则表」、queue 是「收件信箱」）（Fig.13–14, p.11–12）：exchange 是 broker 上虚拟主机里的路由代理，按 exchange 类型决定匹配算法；queue 是命名 FIFO（先进先出：先到的消息先被取走）缓冲；binding 描述 exchange 到 queue 的路由关系（p.11–12）。

![[2-Fig2_p12.png]]
*图 Fig.14（p.12）：AMQP 分发模型——direct 按 routing key 精确匹配，topic 按 routing pattern（通配符）匹配，fanout 无条件广播；每条路径经 bindings 落到具体 queue 再送达 subscriber。*

**图解**：紫色大框是 AMQP Broker，框内从左到右三栏：exchange 栏列出 direct、topic、fanout 三种类型；中间 bindings 栏写明各自的匹配方式——direct 靠 routing key（路由键）精确匹配，topic 靠 routing pattern + routing key（通配符模式匹配），fanout 标注 route message unconditionally（无条件转发）；右侧 queues 栏是五个信箱图标（queue1–queue5）。消息流向从左往右：Publisher₁ 的绿色粗箭头把消息送进 exchange，消息按 binding 规则被投进一个或多个 queue；右侧 Subscriber₁–₅ 中，Subscriber₁ 标 request（一对一请求取用），其余标 subscribe（订阅），消息经 send message（橙色箭头）送达。读图结论：**exchange 类型决定「消息怎么挑队列」——精确匹配、模式匹配还是全量广播；同一套队列设施可同时服务一对一与扇出两种用法**。与毕设的关系：MQTT 只有 topic 一层匹配，这套 exchange 语义是「更灵活的订阅过滤」的参考样板。

- **四种 exchange 类型**（p.12–13）：**direct**（routing key 与 binding key 精确匹配；点对点，一 key 多队列时可多播）；**topic**（routing key 是模式，通配符 `*` 匹配一个关键词、`#` 匹配零或多个，关键词以 `.` 分隔；典型 pub/sub）；**fanout**（不看 key，无条件广播给所有绑定队列；事件通知）；**header**（不看 key，按消息头属性 + `x-match` 的 AND/OR 匹配路由）。
- **送达保证三档**：at most once / **at least once / exactly once**；QoS 两模式 unsettled（不可靠）/ settled（可靠）；安全 **SASL**（Simple Authentication and Security Layer，简单认证与安全层：一套可插拔的登录认证框架）+ **TLS**（Transport Layer Security，传输层加密：https 给网页套的那层「加密信封」）；传输层 TCP（可跑 SCTP，另一种少用的可靠传输协议）（p.13）。生态：Apache Qpid、Azure Service Bus/IoT Hub、IBM MQLight、Amazon SQS（p.13）。

### E. DDS（p.13–14）
- **含义**：OMG 中间件 + API 标准；**data-centric + brokerless**——发布/订阅通过"**全局数据空间**（global data space：可想象成所有设备共用的一块白板，谁都能往对应栏位写数据，想要的人盯着栏位看，无需中转台）"完成，无中心服务器，特别适合 M2M（p.13）。
- 两层接口：**DCPS**（核心，发布订阅绑定数据对象值）与 **DLRL**（可选，对接外部实体）（p.13）。
- 核心构件：publisher + **DataWriter** / subscriber + **DataReader**；topic 三元组（name、data-type、可选 QoS 策略）；**23 种 QoS 策略**覆盖安全、优先级、durability、reliability 等（p.13）。

![[2-Fig3_p13.png]]
*图 Fig.15（p.13）：DDS 数据中心模型（global data space）——各 DomainParticipant 直接对 topicA/B/C publish/subscribe，topic 自带 QoS；无 broker，参与者彼此时间解耦。*

**图解**：中央浅蓝云朵就是「全局数据空间」（global data space），里面放着三个主题框 topicA/topicB/topicC，每个右上角都标着 QoS——主题自带服务质量策略。左侧 Participant₁、Participant₂ 沿蓝色箭头 publish（写入主题）；右侧 Participant₃、Participant₄ 沿绿色箭头 subscribe（读取主题）；参与者彼此不直连，全部通过这块共享云完成交换。读图结论：**没有 broker，「全局数据空间 + 动态发现」替代了中心中转**；同一主题可多人写、多人读，参与方在时间上解耦。与毕设的关系：DDS 展示了与 MQTT 相对的「无中心」路线——毕设保留 broker 是为了轻量与可控，但「topic 自带 QoS、按主题声明可靠性等级」的做法值得借鉴。

- 机制要点：DomainParticipant 让应用加入一个或多个域，同域即可互通；**发布/订阅时间解耦，各自拥有通信网络，支持 D2D 实时交互**；数据模型源自关系模型（管 schema + 内容查询/过滤）；**动态发现无需服务器**；厂商互操作靠 **RTPS**（Real-time Publish-Subscribe：DDS 各厂商实现之间互通的「普通话」协议）有线协议；安全由 Security Model + **SPI 插件**（可插拔扩展接口：按统一接口替换安全组件的实现）扩展；编码可用 **CBOR**（二进制、消息小于 JSON）（p.13–14, 18）。

### F. XMPP（p.14）
- **含义**：源自 Jabber 的开放标准，XML（用标签组织的文本格式，人能读但体积大，如 `<temp>23</temp>`）over TCP 的 client/server 架构，IM（Instant Messaging，即时通讯）起家；核心服务之外靠 **XEP 扩展**（350+ 个），其中 **PubSub XEP 才使 XMPP 支持 publish-subscribe**，从而可用于 IoT（p.14）。
- 实体标识为 **JID**（`xmpp_user@xmpp_server/resource`）；bare JID 无 resource，full JID 带；同一账号可挂多个 resource（多设备）（p.14）。
- 机制与短板：stanza 交换是 **fire-and-forget，无送达保证**；presence 靠订阅模式广播在线状态；**不支持 D2D**；服务器可联邦（federation）/集群（clustering）做动态资源发现；XML 文本编码带来**高开销**（p.14）。*Fig.16（XMPP 智能家居示例, p.15）未选用，要点如上。*

## 六、discussion：九个维度（p.15–26）
### A. 互操作性（p.17–18）
- 三层互操作问题：**通信模式**（设备支持的 pattern 不同）、**语法**（payload 格式不同——CoAP/JSON 设备发的消息，XMPP/XML 设备解析不了）、**语义**（同一数据被不同组件解读不同）（p.17–18）。
- 工程解法：**Azure IoT Edge Runtime 作协议翻译网关**——网关懂设备的私有协议（BLE、RJ485 等），翻译成云理解的 HTTP/MQTT/AMQP；网关还能顺带跑边缘 AI 推理（Fig.17, p.17）。语义层有 LOD4IoT、SWoT、W3C WoT Thing Description（JSON-LD）等方案（p.18）。
- DDS 的 CBOR 编码（消息小于 JSON、可扩展 tag）提升异构数据模型间的互操作（p.18）。

### B. 服务供给（p.18–19）
HTTP 是 REST 服务的事实标准；SOAP（基于 XML 的老式 Web 服务消息格式，比 JSON 臃肿）消息太大不适合受限设备；**CoAP 可与 HTTP 互操作，让受限设备以 REST 方式绑定服务**；SOAP-over-XMPP 是 XEP-0072；DDS 本不支持 HTTP 访问，RESTful DDS 补位；RabbitMQ/Paho 等提供 REST 接口（p.18–19）。

### C. 微服务与分布式追踪（p.19）
- HTTP 有 Zipkin/OpenTracing/Dapper/Jaeger 等成熟分布式追踪；**非 HTTP 协议（MQTT、AMQP）的追踪支持非常匮乏，pub/sub 模式的追踪几乎空白**——随着边缘侧微服务化，这是 IoT 可观测性的关键缺口（p.19）。

### D. 可扩展性与性能模型（p.19–21）
- **订阅扇出的数学模型**：设客户端集 C = {c1…cn}，平均订阅主题数 topic_average，则总传输数 **trans_msg = n × topic_average**；最坏情况（全员订阅全部主题）= **n²**。总时间 transtime = trans_msg × time_msg。例：100 客户端、平均 10 ms/条 → **1.67 分钟**（p.20）。
- **为什么需要**：说明中心 broker 的消息传输随订阅规模平方级膨胀，broker 资源耗尽即成为 **SPoF**（Single Point of Failure，单点故障：这一个部件挂掉、整个系统跟着停摆，像唯一的独木桥）——这是 MQTT 架构级短板（p.20）。
- 缓解方向：MQTT 是 D2C 流，可用 serverless 提升弹性；示例系统（Fig.19, p.20）：ESP32（一款廉价的物联网 Wi-Fi 单片机开发板）空气质量节点 → **mDNS/DNS-SD 零配置发现**（局域网内不设服务器就能自动互相发现）→ 树莓派 fog 网关（[[雾计算]]：把「云」的职责下沉到本地基础设施层跑，fog 即贴地面的雾）→ MQTT 上 AWS IoT Core → 云端 serverless（无服务器架构：代码交给云平台按需运行，不必自己管服务器）消化发布负载；节点离云越远时延越高（p.20）。
- broker 实测差异 [111]：Mosquitto/HiveMQ/BevyWise 单客户端单主题约 1 msg/s（QoS 1）；**10 个并发订阅者摊薄到 0.1 msg/s**——订阅者越多送达率越低（p.21）。
- 相关实测结论汇总：MQTT 吞吐随订阅数上升显著下降 [112][113]；**DDS 高性能、MQTT 往返时延明显恶化** [114]；MQTT 在时延/丢包/字节上优于 CoAP [115]；MQTT-SN 优于 CoAP [116]；AMQP 略优于 MQTT 与 CoAP，且 CoAP 比 MQTT 吃算力、AMQP 两头都吃 [118]（p.21）。
- 定性结论：**CoAP 与 HTTP 有传输额外开销，不适合实时边缘/fog 系统**；MQTT 依赖云性能引入网络时延；broker 一般 **100–1000 msg/s/订阅者** [20][117]；XMPP 不适合低时延；**DDS 部署在 LAN（Local Area Network，局域网）、用 UDP 多播（一次发送、组内所有成员同时收到），可扩到千级节点每节点 1000 msg/s，适合边缘/fog 分布式部署**（p.21）。

### E. 性能实测文献汇总（p.21–22）
1. **时延**：[151] 双测试台（fog MQTT broker vs 云 MQTT broker），HTTP 响应时间显著高于两者（数值 12.1 与 4.76，**单位在提取文本中缺失，原文应有标注**）；**本地 fog 环境下 QoS 1 的丢包是 QoS 0 的 6.2 倍**（p.21）。[152] 家居测试台：MQTT 时延远低于 HTTP。[4] 低丢包 MQTT < CoAP，高丢包反超。[153] CoAP 带宽/响应时间更优，适合 fog/edge。[154] JS 客户端：**MQTT 时延最低，其次 AMQP，XMPP 与 DDS 高且接近**。[118] 小 payload 少消息：CoAP > MQTT > AMQP > DDS；**消息数增到 1000 条：DDS > CoAP > AMQP > MQTT——MQTT 最差**（Fig.20, p.22）；大 payload（>50 KB）排序类似，DDS 仍最优，CoAP 全场稳定（p.21–22）。
2. **吞吐**：[152] MQTT 每小时消息数最高且大消息量下功耗最低；[157] AMQP 带宽远高于 RESTful HTTP；[158] CoAP 在送达率/时延/开销上优于 HTTP；[5] CoAP 小 payload 最佳、大 payload 恶化（p.22）。
3. **CPU/内存/功耗**：[118] 内存 DDS > AMQP > CoAP > MQTT；CPU AMQP > DDS > MQTT > CoAP（小/大 payload 均如此）；[152] **功耗 HTTP = 5.3 × MQTT，CoAP = 1.9 × MQTT**（p.22）。
- 作者的方法论批评：各研究测试环境不一致——QoS 级别不同、是否含初始化时间不明、实现语言影响结果，横向比较要小心（p.22）。

### F. 可靠性（p.22–23)
- UDP 省带宽但**无流控、无差错控制、无重传**（p.22）。CoAP 用 CON 重传补救，但**没有内建机制验证消息被完整接收/正确解码**；DTLS 不支持多播、握手要补包；CoAP **不做 mobility management**（移动性管理：设备换网后系统仍能找到它）——设备跨网移动拿到新 IP 后系统找不到它，NAT（网络地址转换：路由器把内网设备藏在同一公网地址后面，外部无法主动找进来）后的资源发现也会失效（p.22–23）。
- XMPP：连续 TCP 流保证 stanza 有序到达（避免 Two Generals Problem——分布式系统经典难题：双方仅靠不可靠信道传信，永远无法百分之百确认对方状态一致），**XEP-0198** 在移动网络多会话上增强 TCP 可靠性（p.23）。
- DDS：DataWriter/DataReader 可声明 **reliability QoS policy** + redundancy/重试，但可靠性越高端侧处理开销越大（p.23）。

### G. 安全（p.23–24)
- 共性风险：几乎全员基于 **TLS**，TLS 层的攻击面是共同的；IoT 设备算力不够跑复杂安全操作，天然易被攻击；五个脆弱源：**devices / connectivity / computing / storage / microservices**（p.23）。
- 分析框架：CIA（机密/完整/可用）+ IEEE AAA（认证/授权/审计）。**设备完整性**在消息协议层的具体形态：攻击者订阅已有 publisher 窃数据——TLS 只管传输安全，**不管"谁有权订阅/发布"**（p.23）。
- **QoS 2 的机制缺陷解释了为什么很多云平台不提供 QoS 2**（p.23，另见 §四.C 的 UTF-8 DoS）。
- 各协议：AMQP 用 **SASL** 做授权；**DDS Security Model 最全面**——5 个 SPI（authentication、cryptography、access control 等，Table 10, p.24），libddssec 开源库（限 ARM TrustZone）；XMPP 用 **Authorization Tokens**（token 替代密码，避免设备存密码）（p.23–24）。

### H. 适应性与扩展性（p.24–25）
- **XMPP 原生扩展性最强**（XML + 300+ XEP：XEP-0076 Malicious Stanzas、XEP-0030 Service Discovery、XEP-0080 User Location 等）；DDS 有 **DDS-XTypes**（数据类型可演化而不改程序——自动驾驶案例：车 A 只发经纬度、车 C 多发乘客数，XTypes 让两种数据类型在同一系统共存；Volkswagen、Audi 已采用 DDS）；RabbitMQ 有 per-queue message TTL 等；**HTTP/CoAP/MQTT 扩展支持很有限**（p.24–25）。

### I. 实现与采用率（p.25–26)
- **实现体积悬殊到三个数量级**：CoAP-Lite 约 **14 KB**（Linux）、CoAP.NET 超 10 MB，而 RTI 的 Windows DDS 实现超 **640 MB**（文中另提到 DDS 库有时 >2 GB，见 p.28 优缺点表）——受限边缘设备根本装不下 DDS 客户端，CoAP 反而合适（p.25–26）。
- Eclipse 调查（2015–2018, Fig.22, p.26, **图未在图源目录中**）：HTTP 2018 年下降约 9% 但仍居前二；**MQTT 2017→2018 显著上升**；AMQP 逐年渐升；CoAP 2019 年跌破 15%；DDS 持平。参与者人数 2015:394 → 2017:713 → 2018:502 → 2019:1717（2018 年降 30%+，解读趋势要小心）（p.26）。
- 调查与云平台支持互相印证：HTTP、MQTT 前二，AMQP 第三，XMPP 第五（p.26）。

## 七、各协议优缺点总结（p.26–28, Table 14）
- **MQTT**：优——轻量、异步、事件驱动可伸缩、QoS 0/1/2、**几乎所有云平台支持**；劣——**不支持大 payload**、topic 名偏长（对 LR-WPAN（Low-Rate Wireless Personal Area Network，低速率无线个域网：ZigBee 那类短距低功耗网络）不友好）、不适合多媒体、**不支持 D2D（仅 D2C）**、无动态发现、**broker 是 SPoF**、TCP 长连接限制受限设备休眠、加密靠 TLS/SSL 增加连接开销（p.27）。
- **CoAP**：优——4 字节头、动态资源发现、适合受限设备、UDP 可跑在 SMS 等分组技术上；劣——QoS 层级有限、**只适合 D2D 不适合 D2C**、只有 DTLS（无 SSL/TLS）、不易扩展、易受 spoofing（受限网络内端点可随意读写消息）（p.27）。
- **AMQP**：优——队列负载均衡、支持（分布式）事务、连接多路复用、离线取件；劣——可靠性受限于传输层、无动态发现、无多播、broker SPoF、消息流慢且复杂、出身金融业非为 IoT 设计（p.27–28）。
- **XMPP**：优——分布式 client/server 设计、SASL 认证、XML 带来最强扩展性；劣——**无 QoS/送达保证**、无端到端加密、XML 开销大、server SPoF（p.28）。
- **DDS**：优——**近实时（1-to-1 时延低至 30 µs）**、23 种 QoS、无 SPoF、peer-to-peer/D2D/D2C/C2C 全覆盖、最全面的安全模型；劣——**实现库极大（有时 >2 GB）**、实现复杂、不适合算力受限的边缘设备（p.28）。
- **HTTP**：优——REST + URI、分布式追踪工具链、可穿防火墙；劣——header 大、时延高、文本编码、**无 QoS**、不易扩展（p.27）。

## 八、conclusion（p.28）
**六协议相似性足以共存**；异构 IoT 系统本来就常用多协议，理解各自强弱是选型与降低维护成本的前提；互操作（协议翻译、语法/语义桥）是后续关键方向。作者未来工作：按系列 IoT 用例做实测性能对比，并把 HTTP 2.0 与 WebSocket 纳入考察（p.28）。

## 对毕设的帮助

### 写论文
- **"为什么选 MQTT"的理由链**（任务1）：最小包 2 字节 vs HTTP 头 200 B–2 KB（p.2）、功耗 HTTP=5.3×MQTT（p.22）、十大云平台全部支持 MQTT（p.7）、Eclipse 调查采用率上升趋势（p.26）——四个证据拼成"轻量级消息中间件选 MQTT"的完整论证；同时用本文承认的短板（大 payload 最差、SPoF、不支持 D2D，p.27）界定毕设系统的适用边界。
- **协议评估表骨架**（第二章写作）：九维比较框架（互操作/服务供给/微服务追踪/扩展性/性能/可靠性/安全/适应扩展/实现与采用率，p.15–26）可直接改造成毕设第二章的协议评估表，每维引用本文给出的文献结论并标注出处页码。

### 动手实现
- **QoS 0/1/2 模块**（任务3）：实现注意三点——QoS 级别在 Connect Flags 的 Will QoS 位（bits 4/3）指定（p.10）；**QoS 越高 broker 开销越大，QoS 2 + 多订阅者是最重场景**，需单列优化路径；topic 命名要短（长 topic 名对 LR-WPAN 不友好，p.27），网关侧可做 topic 缩写映射。
- **可靠性机制**（任务4）：broker 入口必须校验 topic/字符串（UTF-8 非法码点 + retain + QoS 2 的 DoS 链，p.11）——这是"遗嘱消息/持久化"之外容易被忽视的输入校验点；可靠性与开销的权衡参照 [151] 的 QoS1 丢包 6.2× 结论；CoAP 的 CON/ACK 重传模型（同 message id 的 ACK, p.9）可作为 MQTT QoS 1 PUBACK/PUBREC 握手的对照实现参考。
- **边云桥接与组网**（任务5）：单 broker 是 SPoF（p.20）——多节点组网的核心目标就是消除它：桥接冗余、broker 集群或分布式 broker（论文8 方向）；协议翻译网关模式（Azure IoT Edge，p.17）可直接借鉴为毕设网关的**多协议接入层**设计——网关对下吸收设备私有协议，对上统一成 MQTT。

### 测试
- **负载预估模型**（任务6）：**trans_msg = n × topic_average（最坏 n²）**（p.20），据此设计连接数/订阅扇出梯度（如 10/50/100 客户端 × 全订阅）。
- **基线数字**：broker 100–1000 msg/s/订阅者（p.21）；单客户端 QoS 1 约 1 msg/s 的历史实现（p.21）。
- **测试变量与指标口径**：**payload 尺寸必须作为测试变量**（5 KB / >50 KB 两档，结论会反转：小 payload CoAP/MQTT 好，大 payload DDS 最优、MQTT 最差，p.21–22）；指标至少含时延、吞吐、丢包率、内存/CPU（排序见 p.22）；丢包率按 QoS 0/1/2 分组统计；横向比较需记录 QoS 级别、是否含初始化时间、实现语言等口径（p.22 方法论批评）。

**在树莓派上**：
- 树莓派当「受限设备」角色：分别用 HTTP 上报（python3 + requests）与 MQTT 上报（paho）各跑 1 小时，对比耗电与内存——对应本文功耗 HTTP = 5.3 × MQTT 的量级感（p.22）。

**C++ 实现要点**：
- broker 入口必须做输入校验（p.11 的 DoS 链：非法 UTF-8 topic + retain + QoS 2 可打断订阅端）：topic 长度上限 + UTF-8 合法码点检查，不合格直接拒收并断开。
- topic 命名约定要短（长 topic 对低速率链路不友好，p.27）；网关侧做「设备原始 topic ↔ 短 topic」缩写映射，映射表用 `std::unordered_map` 即可。
