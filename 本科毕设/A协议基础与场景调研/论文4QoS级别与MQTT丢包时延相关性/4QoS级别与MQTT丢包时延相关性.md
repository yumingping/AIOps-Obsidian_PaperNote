## 一、abstract/introduction（p.1）
### 痛点 / 已有方法为什么不行
- **QoS 级别的代价差异没人量化**：[[MQTT（消息队列遥测传输）]]（MQTT：极轻量的消息传输协议，设备把消息发给中转站 [[Broker（消息代理）]]（broker：居中转发的服务器，像快递驿站——所有包裹先到驿站再分发，收发双方不用见面）、订阅者从驿站取）用三级 [[QoS（服务质量）]]（Quality of Service：消息送达的「保险等级」，等级越高越不丢、但越慢）保证消息可靠性（p.1）。**QoS 0** 只发一次、不确认送达，大消息可能丢失（[[丢包率]]：发出去但没送达的消息占比，像寄 100 封信寄丢 2 封，丢包率就是 2%）；**QoS 1** 靠 **[[PUBACK（发布确认）]]**（publisher 发出消息后 broker 回的一句「收到了」，像快递签收回执）状态检查保证 at-least-once（至少送达一次，可能重复），但 **PUBACK 丢失时 broker 因无送达确认而重发，可能收到重复消息**；**QoS 2** 走 **[[QoS 2 四次握手（4-way handshake）]]**（双方来回确认四次才承认「这条消息送达且只有这一条」，像签合同一式两份双方各留底，确保不丢不重）保证 exactly-once（恰好送达一次）、不丢消息，但**握手流程复杂导致[[端到端时延]]（一条消息从发出到被接收方收下经过的全部时间，像快递从寄出到签收的总时长）显著变长**（p.1）。
- **QoS 越高交换报文越多**：不想丢消息就选高 QoS，但复杂流程推高端到端时延——**两条曲线的 trade-off 缺少定量依据**（p.1）。
- **已有工作不可靠**：Julio 等在 OMNeT++（一款网络仿真软件：在电脑里虚拟出网络做实验，不用真设备）仿真环境中分析 MQTT 性能（含 Gilbert-Elliot 无线建模：一种模拟无线链路「时好时坏」的数学模型），但**仿真难以可信地反映真实网络环境下的性能**（p.1）。

### 新方法（一段话）
在**真实的有线/无线商业网络**里搭 publisher → broker → subscriber 链路，用真实[[抓包（packet capture）]]（把网络上流过的每个数据包原样记录下来存成文件供事后分析，像在路口装行车记录仪）而非仿真，测不同 [[payload（消息载荷）]]（一条消息里真正要传送的数据内容，不算报文头等「信封」开销，像快递里的货物本身，大小以 bytes 计）大小、不同 QoS 级别下的端到端时延与丢包，并做两者的**相关性分析**——若能算出「丢包—时延」随 payload 与 QoS 的关系，就能为 push 通知类服务选出合适的 QoS 级别，搭建最优服务网络（p.1）。

**核心机制图**：三级 QoS 的报文交换序列（QoS 0 仅 PUBLISH；QoS 1 为 PUBLISH→PUBACK 两报文；QoS 2 为 PUBLISH→PUBREC→PUBREL→PUBCOMP 四次握手）——

![[4-Fig1_p1.png]]
*图1（p.1）：三级 QoS 的报文交换方法——QoS 0 一报文、QoS 1 两报文、QoS 2 四次握手，交换报文数逐级增多。*

**图解**：图里并排画了三组时序图（sequence diagram：从上往下按时间顺序画双方互发的报文，每支箭头代表一个报文及其方向），每组左边是 Publish/Subscribe Client（发消息的客户端，电脑图标）、右边是 Broker Server（中转服务器，服务器图标），两条竖线之间的横向箭头就是报文。怎么看：左栏 QoS 0 只有一支向右的箭头（PUBLISH 发出去就完事）；中栏 QoS 1 两支（PUBLISH 去、PUBACK 回执回来）；右栏 QoS 2 四支（PUBLISH 去、PUBREC 回、PUBREL 去、PUBCOMP 回，四个来回）。读图结论：**保险等级每升一级，报文数逐级增多**——QoS 2 一条消息要四个报文才算送达，这正是它时延最高的直接原因。与毕设的关系：任务 3 实现 QoS 0/1/2 通信模块时，报文时序照此图实现；测时延时可用报文数估算各级的理论开销下限。

## 二、methodology（p.2）
### 实验环境（p.2）
1. **软件栈**：server 用 Linux CentOS 6.3 Final；broker 用开源 **Mosquitto**（p.2）。
2. **消息链路**：Publish client 声明 topic 并发消息给 broker；broker 维护 topic 并在 Subscribe client 订阅后充当中转（Figure 2, p.2，未提取，图示为多 topic 消息按订阅关系分发的过程）（p.2）。
   - **图解**（Figure 2, p.2，未提取）：publisher 按 topic（消息的「频道名」）把消息发给 broker，broker 手里有一张「谁订了哪个频道」的登记表，按表把消息分发下去——多个 topic、多个订阅者时各自对号入座。读图结论：broker 的核心工作就是「订阅表匹配 + 转发」。与毕设的关系：broker 模块的功能边界与 topic 设计（订阅表怎么建、怎么查）可照此理解。
3. **有线/无线对照组**（Figure 3, p.2，未提取）：**故意把客户端放在外部网络、让 broker 的访问穿过商业网络核心**，以构造贴近真实的时延/丢包环境；无线客户端用 **Android 2.3**，流量经 **3G** 网络到 broker（p.2）。
   - **图解**（Figure 3, p.2，未提取）：实验拓扑图——节点（客户端、broker）与连线表示网络路径；关键在路径走向：客户端不在本地局域网，而是绕经外部商业网络核心再回到 broker，无线一侧经 3G 蜂窝网。读图结论：测得的时延与丢包是真实商用网络的值，不是实验室理想值——这是该文可信度的来源。与毕设的关系：测边缘场景性能时要包含跨公网/无线链路的对照组，不能只在实验室局域网里测。

### 抓包与分析方法（p.2）
- **含义**：有线用 **Tcpdump** 抓包存 pcap，无线端受移动环境限制改用 shark 应用抓包存 pcap；pcap 统一用 **Wireshark** 分析（p.2）。
- **指标口径**：测量窗口 **5 分钟**；**端到端时延 = 报文从 Subscribe server 经 broker 到 Publish client 沿途时间戳的累差**；**丢包 = 统计 5 分钟内 retransmission request（重传请求：接收方发现少了一段数据，喊一声「没收到，请重发」）报文数**（p.2）。

## 三、实验结果（p.2–3）
### 有线网络（p.2–3）
![[4-Fig4_p3.png]]
*图4（p.3）：有线网络平均端到端时延——payload >4,000 bytes 后分片增多、时延上升；QoS 2 全程最高。*

**图解**：折线图。横轴是 payload（消息大小，单位 byte，从 1,000 到 16,000），纵轴是端到端时延（秒，0–0.16）；三条线分别是 QoS 0（蓝实线）、QoS 1（红点划线）、QoS 2（绿虚线），越靠上越慢。怎么看：所有曲线在 4,000 bytes 后都明显抬头（分片增多），且三条线高低分明——QoS 2 全程最靠上（约 0.100–0.135 s），QoS 1 居中（约 0.045–0.093 s），QoS 0 最靠下（约 0.027–0.073 s）。读图结论：**时延 QoS 2 > QoS 1 > QoS 0**，且都随 payload 变大而上升；QoS 2 在 8,000 bytes 之前近似平坦、之后明显上翘，与正文结论一致。与毕设的关系：选 QoS 与定消息大小上限的依据——小消息用低 QoS 够用，追求低时延就别盲目上 QoS 2。

- **时延（p.3）**：**payload 超过 4,000 bytes 后报文分片数增加，端到端时延随之拉长**；QoS 2 时延最高的主因是 4-way handshake；**QoS 2 在 payload < 8,000 bytes 时端到端时延变化不明显**（图中 QoS 2 曲线在 1,000–8,000 bytes 区间近似平坦，8,000 bytes 后上翘，与该结论一致）。
- **丢包（p.3）**：正文称 **QoS 2 相比 QoS 0 或 1 把消息丢失降低约 1.57 倍**；图5 显示消息丢失随消息增大而上升，QoS 2 靠 4-way handshake 把丢失压到最低（图中 QoS 2 全程 ≈0.03–0.15%，QoS 0/1 ≈0.85–1.37%）。

![[4-Fig5_p3.png]]
*图5（p.3）：有线网络丢包——QoS 0/1 随 payload 上升至 ~1.4%，QoS 2 始终压在 0.15% 以下。*

**图解**：折线图。横轴同样是 payload（1,000–16,000 bytes），纵轴换成丢包率（%，0–1.6%）；配色与图 4 相同（QoS 0 蓝实线、QoS 1 红点划线、QoS 2 绿虚线）。怎么看：绿线（QoS 2）几乎贴着横轴（约 0.05%–0.16%），蓝线和红线随 payload 从约 0.9%–1.0% 爬到 1.1%–1.36%，payload 越大爬得越快。读图结论：**丢包率 QoS 0 > QoS 1 > QoS 2**，与图 4 的时延排序正好相反——QoS 2 用四个报文的时延代价把丢包压到接近零，「可靠性是花钱（时延）买来的」在这两张图上一目了然。与毕设的关系：可靠性论证可直接引用这组数字（QoS 2 ≈0.15% vs QoS 0/1 ≈1.1–1.4%）。

### 无线网络（p.3）
- **时延（p.3）**：无线（3G）时延整体显著高于有线，主因是 3G 传输速度；图6 数值量级 0.4–1.0 s（有线仅 0.03–0.14 s）（Figure 6, p.3，未提取）。

**图解**（Figure 6, p.3，未提取）：与图 4 同类型的折线图——横轴 payload、纵轴端到端时延，但纵轴刻度抬到 0.4–1.0 s 量级，曲线整体上移且波动更大。读图结论：无线链路时延比有线高约一个数量级，瓶颈在 3G 传输速度而非 QoS 流程本身。与毕设的关系：边缘节点若走蜂窝网/Wi-Fi，时延预算要按 0.4 s 起估，不能沿用有线量级。
- **丢包（p.3）**：正文表述「消息丢失率较为稳定，QoS 2 低于 QoS 0 或 1」；**图7 实际显示 payload 升至 16,000 bytes 时 QoS 0/1 陡升至约 25–27.5%、QoS 2 升至约 16%**——正文「较稳定」的说法与图不完全一致，如实记录（Figure 7, p.3，未提取）。

**图解**（Figure 7, p.3，未提取）：同为 payload-丢包折线图，但纵轴刻度飙升到 25% 上下。怎么看：payload 较小时三条线都不高，到 16,000 bytes 处 QoS 0/1 陡升到约 25–27.5%、QoS 2 升到约 16%——曲线末端像悬崖。读图结论：无线链路上大 payload 会触发丢包放大，QoS 2 的四次握手能缓解但救不回量级。与毕设的关系：边缘无线链路必须设消息分片/大小上限，避免落到悬崖右侧。

### 相关性分析（p.3–4）
- **含义**：对每个 QoS 级别计算端到端时延与丢包的相关系数 $r$，$r \in [-1,1]$，越接近 1 正相关越强（p.3）。变量 $n$ 为每个 QoS 级别下测量的 payload。相关公式（原文公式 (1)）**在提取文本中残缺**，仅可辨认均值、标准差符号与 $r$ 取值范围；按符号构成推断为 Pearson 相关系数（此推断为推测，未从原文逐字确认）。
- **公式增补（原文残缺，按 Pearson 推断补全）**：$r = \dfrac{\sum_{i=1}^{n}(x_i-\bar{x})(y_i-\bar{y})}{\sqrt{\sum_{i=1}^{n}(x_i-\bar{x})^2}\,\sqrt{\sum_{i=1}^{n}(y_i-\bar{y})^2}}$
  - 逐符号：$r$ = [[相关系数（correlation coefficient）]]（衡量两个量是否「同涨同跌」的数值，范围 -1 到 1：1 = 完全同步涨跌，0 = 毫无关系，-1 = 一个涨另一个必跌）；$n$ = 每个 QoS 级别下测量的 payload 档位数（即该级别做了几次不同大小的实验）；$x_i$ = 第 $i$ 次实验测得的端到端时延；$y_i$ = 同一次实验测得的丢包率；$\bar{x},\bar{y}$ = 所有实验时延/丢包的平均值（先各自减去均值，是只看「偏离各自平均水平的波动」是否同步，避免绝对值大小干扰）。
  - 大白话翻译：把每次实验的时延和丢包各画成一个点，这条公式算的是这些点排成的形状有多接近一条上升直线——r 越接近 1，说明「哪次实验时延大，那次丢包也倾向大」，两个指标是一根绳上的蚂蚱，动一个必然牵动另一个。此补全为推断（原文公式残缺），数值结论（Table I）以原文为准。
- **结果（Table I, p.4）**：

| QoS 级别 | 有线网络 | 无线网络 |
|---|---|---|
| QoS 0 | 0.771574 | 0.878897 |
| QoS 1 | 0.788814 | 0.884428 |
| QoS 2 | **0.991416** | 0.904699 |

- **核心结论**：**各 QoS 级别下端到端时延与消息丢失均呈强正相关**（$r$ 全部 > 0.77），即「时延大时丢包也大」，两者紧密关联（p.4）。有线 QoS 2 相关系数最高（0.991），几乎线性绑定。

## 四、conclusion & future work（p.4）
- 实验比 OMNeT++ 仿真更贴近真实网络；**端到端时延与丢包在不同 payload 下显著相关**（p.4）。
- **按 payload 选择合适的 QoS 级别**，即可搭建更高效的 push 通知服务网络（p.4）。
- 未来工作：更多 QoS × payload 组合求最优 QoS 配置；分析 broker 性能、多客户端通信、不同 topic 数下的吞吐（p.4）——这三项分别对应 broker 基准测试与多 topic 场景，是后续可扩展的测量维度。

## 对毕设的帮助

**写论文**
- 对应任务3的 QoS 设计章节，可引用的结论数字：有线网络 QoS 2 丢包 0.03–0.15% vs QoS 0/1 约 0.85–1.37%（p.3 图5）、「QoS 2 相比 QoS 0/1 把消息丢失降低约 1.57 倍」（p.3）；有线时延 0.03–0.14 s、无线 3G 0.4–1.0 s（p.3）；各 QoS 级别下时延与丢包强正相关（r 全部 >0.77，有线 QoS 2 达 0.991，Table I p.4）。
- 论证「真实抓包优于仿真」时引用其对 OMNeT++ 类仿真的批评（p.1）；payload >4,000 bytes 分片导致时延上升（p.3）可支撑消息大小上限的设计论述。

**动手实现**
- QoS 选型判据（任务3）：payload ≤4,000 bytes 用 QoS 0/1（时延增长平缓），数据完整性优先、能容忍时延的关键控制/告警消息用 QoS 2。
- QoS 1 的 PUBACK 丢失会引发 broker 重发（p.1）——订阅端必须做幂等/去重处理，可结合 MQTT 报文 packet id 实现（本文只点名现象，去重逻辑需自行设计）。
- 边缘节点间设消息分片/大小上限：无线 16,000 bytes 处丢包陡升的悬崖（p.3 图7）说明大 payload 在无线链路上会触发丢包放大。
- 把 QoS 级别选择本身当作一项可靠性配置项，与遗嘱消息、断线重连并列写进系统设计（任务4）。

**测试**
- 整套实验设计可直接照搬（p.2–3）：①真实环境而非仿真；②有线/无线双对照组；③Tcpdump/shark 抓包存 pcap、Wireshark 分析；④固定测量窗口（本文 5 分钟）；⑤payload 梯度 1,000/2,000/4,000/8,000/16,000 bytes；⑥指标口径——时延 = 沿途时间戳累差、丢包 = 窗口内重传请求计数；⑦最后算相关系数把两个指标串起来。
- 增补建议（本文未测）：补 [[抖动（jitter）]] 口径——统计相邻报文到达时间差的波动（Wireshark IO Graph 的 inter-arrival time 可直接给出），控制/告警类业务对抖动往往比平均时延更敏感。
- 吞吐/连接数测试可在同一抓包管道上加指标，不必重搭环境；其 future work（p.4）点名的 broker 性能、多客户端、多 topic 三个维度与毕设任务6的测试计划对得上。

- 按本文规程复现（p.2–3）：① payload 梯度 1000/2000/4000/8000/16000 bytes，`mosquitto_pub -q {0,1,2} -t qos/test -f payload.bin`；② `sudo tcpdump -i eth0 -w qos.pcap port 1883` 固定测 5 分钟一窗；③ `tshark -r qos.pcap -Y 'mqtt' -T fields -e mqtt.msgtype -e frame.time_relative` 统计报文与时延；④ 指标口径对齐本文：丢包 = 窗口内重传请求报文数。
- 结果画成图 4/图 5 的折线：横轴 payload、纵轴时延/丢包、三条 QoS 曲线。

**在树莓派上**：
- 无线对照组：树莓派连 Wi-Fi 热点发 16 KB 消息，观察 p.3 图 7 的「悬崖」（大 payload 无线丢包陡升到 25%+）——这就是消息分片/大小上限的直接依据。

**C++ 实现要点**：
- QoS 1 的 PUBACK 丢失会引发 broker 重发（p.1）：订阅端必须按 MQTT packet id 去重，用 `std::unordered_set<uint16_t>` 记录在途/已处理 id。
- 选型做成接口参数而非写死：高频遥测 QoS 0/1，关键控制/告警 QoS 2；消息大小上限默认压在 4000 bytes 以下（分片阈值，p.3）。
