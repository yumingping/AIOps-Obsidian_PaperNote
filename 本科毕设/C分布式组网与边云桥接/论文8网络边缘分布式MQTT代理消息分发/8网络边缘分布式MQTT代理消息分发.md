## 一、preview/abstract（p.1）
### 痛点 / 已有方法为什么不行
- 边缘计算（edge computing：把计算与存储从远端大机房搬到离设备近的「门口小机房」——小区基站、路侧机柜——响应更快、省长途带宽）把存储与处理从远端数据中心下沉到靠近用户的分布式边缘节点，但**网络协议是为集中式管理设计的，自身不会扩展到分布式边缘场景**（p.1）。
- **[[MQTT（消息队列遥测传输）]]**（Message Queuing Telemetry Transport：为低带宽、不稳定网络设计的轻量消息协议）的 broker（[[Broker（消息代理）]]：消息中转站，发布者与订阅者不直接对话、都经它转手）是发布者/订阅者之间的中间人，IoT 数据大多在边缘产生和消费 → 把 broker 部署到边缘计算节点是扩大 MQTT 规模、降低传播时延、省带宽的自然方案（p.1）。
- 分布式发布/订阅系统（发布/订阅，publish/subscribe：发消息的人和收消息的人互不认识，中间隔着按「频道」分拣的中转站）的基本问题：**消息要可靠且高效地在 [[分布式 broker 网络（distributed broker network）]] 内跨 broker 分发**（多个 broker 各管一片设备、彼此连成网，消息要能跨节点送达——好比多个邮局之间要有运输干线）——无论发布者/订阅者连在哪个 broker 上，消息都必须送到所有感兴趣的客户端（例：车联网中每辆车无论连哪段路侧设施，都要收到道路安全告警）（p.1）。
- **已有方案为什么不行**：现有消息分发方案依赖**无条件泛洪**（flooding：把通知复印一份发给所有邻居、邻居再转发给各自的邻居，直到全网都知道；publication 泛洪或 subscription 泛洪），各自独立处理每条消息；而消息的 [[Topic（主题）]]（topic：消息的「频道名」，用斜杠 / 分层的字符串，如 home/kitchen/oven）之间**事实上常常互相包含**——泛洪因此带来大量冗余流量；且边缘链路容量与算力有限，正是可扩展性的瓶颈（p.1）。此前工作（MQTT-ST 生成树 [11]、Banno 异构互操作层 [6][12]、Hasenburg 地理分布式泛洪 [9]、Detti 贪心负载均衡 [13]）**都忽视了 MQTT 以 topic 为中心的本性，不关注 topic 层级**（p.1）。

### 新方法（一段话）
形式化并比较两种现有机制——[[Publication Flooding（PF，发布泛洪）]]（每条发布消息复制给所有 broker）与 [[Subscription Flooding（SF，订阅泛洪）]]（每条订阅复制给所有 broker）——然后利用 MQTT topic 层级与 [[通配符（wildcard）]]（topic 里的「万能牌」：+ 代表任意一层、# 代表其后的所有层）的 [[Topic 包含关系（topic containment）]]（一个 topic 的语义完全落在另一个里面），提出 **[[Selective Subscription Forwarding（SSF，选择性订阅转发）]]**：broker 收到订阅时先与已有订阅做**topic 包含判定**，只有不被已有订阅包含时才向邻居转发，从而 broker 间的订阅永不重复、永不重叠。包含判定可在线性时间完成，所以 SSF 轻量且可行。7 个真实 broker 的实验 + 1000 个 broker 的仿真表明：**SSF 比 SF 减少超过 40% 订阅流量，同时降低 20% 服务时延**（p.1）。

## 二、introduction（p.1–2）
1. 问题直觉（p.1）：分布式 broker 网络中，链路容量与计算能力在**边缘**受限——不像云端资源充足；泛洪式方案在流量重或任何网络元素过载时甚至可能拖垮系统。
2. 相关工作定位（p.1）：Longo 等 MQTT-ST 用生成树协议构建无环 broker 架构；Banno 等设计两种分发算法并用互操作层兼容异构 broker；Hasenburg 等做地理分布式泛洪广播；Detti 等用贪心策略负载均衡——**共同缺陷：不以 topic 为中心**（p.1）。

### 本文贡献（p.1–2）
1. 形式化分布式 MQTT 网络的消息分发问题，梳理现有方案（PF/SF）；
2. 提出 topic 包含问题及高效解法，用以减少 broker 间流量；
3. 在多种网络条件与指标下，通过实验（emulation：在真实软件/硬件上小规模复现，本文是 7 个真实 broker 容器）与仿真（simulation：纯软件模拟，规模可到千级 broker）评估三种机制。

## 三、背景与系统模型（p.2–3）
### MQTT 协议要点（p.2）
1. 基于 topic 的事件驱动发布/订阅，提供时间与空间解耦；轻量可变长消息头，适合资源受限场景（p.2）。
2. 每个 broker 动态维护**一棵 topic tree**（存层级 topic 与各客户端的兴趣；根节点是逻辑节点，全局连接所有一级节点）（p.2）。
3. 通配符：单层 `+`（如 `home/kitchen/+/status`）、多层 `#`（如 `home/kitchen/oven/#`）（p.2）。

### 边缘 MQTT broker 架构（p.2）——本篇核心架构图
- **Fig.3 三层 MQTT 系统架构（p.2，未提取）**：文字描述——三层自上而下为 **Cloud Layer（云端 MQTT broker）/ Edge Layer（边缘 broker 层）/ Device Layer（MQTT 客户端）**；图上边缘层内部标注 "Edge-Based"，云 broker 标注 "Cloud-Based"。
    - **含义**：在云 broker 与 MQTT 客户端之间插入一个由中间 broker 组成的边缘层；**主要的处理与转发都由边缘层承担**，云 broker 只做基本协调与转发，除非需要集中式性能监控或数据聚合——边缘层的 MQTT 功能因此可与云层**解耦**（p.2）。
    - **为什么需要**：IoT 的订阅兴趣大多不跨很大物理距离、broker 负载温和到边缘可处理（p.2）。
    - **图解（Fig.3，未提取）**：图分三层——顶层 Cloud Layer（云图标，标 Cloud-Based，跑云端 broker）、中层 Edge Layer（若干边缘节点图标，标 Edge-Based，跑边缘 broker 且彼此互联）、底层 Device Layer（大量设备图标，各自就近直连一个边缘 broker）。看图要点：消息箭头绝大多数止步于边缘层，只有跨站点聚合/集中监控才上行到云；层与层之间是「客户端→边缘 broker→（必要时）云 broker」的逐级路径。读图结论：**边缘层是主力、云层是协调者**——这就是「边云解耦」的判据：云不可用时边缘层仍能自治工作。与毕设的关系：任务2 总体架构可直接按这三层画，并在图上标明哪些消息只走边缘、哪些必须上云。
- 与已有实现的区别（p.2）：**Mosquitto Bridge 与 HiveMQ Cluster 是为云上多 broker 同步/复制设计的，对外表现为单一云 broker**；本文考虑的是**完全分布式、无云也能工作的边缘 broker**，关注点是**消息分发而非数据复制**——这句话是本篇与集群式 broker（如论文6 测的三家）的分界线。
- 应用场景（p.2）：道路安全/车联网（远端服务器宕机时路侧设施仍要传递安全关键信息）、UAV+移动传感器/执行器网络（地质勘探、灾后恢复）、边缘上的消息类与地理类应用。

### 性能指标（p.2–3）
1. **网络流量**：总流量 + 所有链路中的最大流量（单链路峰值）——边缘带宽宝贵，引入更多 broker 会带来更多 broker 间流量，必须压缩（p.2）。
2. **broker 开销**：连接的 broker/客户端数 + 处理中的消息数；可用处理消息量、CPU 利用率或功耗间接度量（p.2）。
3. **[[服务时延（service latency）]]**：定义为**从 publisher 发出消息到 subscriber 收到消息的时间跨度**——订阅者不知道发布何时发生，无法像请求/响应那样感知时延，但对时敏应用至关重要（p.3）。
4. **Fig.4 动机实验（p.3，未提取）**：7 个 MQTT broker 依次串联通（链式拓扑），100 个 publisher 连在末端一个 broker 上、每人 1 msg/s。随着拥塞加剧、重传增多，服务时延**非线性增长**（超出指数增长预测）：**平均时延在丢包率 0%/5%/10%/15% 下分别为 0.272 / 3.037 / 4.628 / 6.461 秒**；且大量数据包长时间到不了目标接收者。**结论：泛洪过程在网络流量过重或任何元素过载时可能拖垮系统——这就是设计更高效机制的动机**（p.3）。

## 四、问题形式化（p.3）
### 消息分发问题（p.3）
- 每条 publication 必须正确送达所有感兴趣 subscriber，无论 subscriber 连在哪个 broker；客户端无需感知内容来源、也不应按内容主动选 broker——与 MQTT 松耦合/灵活性一致（p.3）。
- **假设网络无环（loop-free）**：从分布式 broker 网络构造无环拓扑可以用 in-band MQTT 消息解决（引 MQTT-ST [11]），不在本文范围（p.3）。

### 订阅包含问题 MSCP（p.3）
1. **定义 1（[[Topic 包含关系（topic containment）]]）**：给定两个层级 MQTT topic x 与 y（按 `/` 分层，允许通配符），$x \sqsubseteq y$（⊑ 读作「被包含于」：符号左边的频道范围完全落在右边之内）表示 x 的**任何可能语义**都包含在 y 中（p.3）。例（Fig.5, p.3，未提取）：`NY/World Trade Center/#`（含路线、告警、now/history 等一切信息）包含 `NY/World Trade Center/+/+/now`（只含 now 的路线与告警）。
2. **定义 2（MQTT Subscription Containment Problem, MSCP）**：给定两条订阅 $s_1, s_2$（topic 分别为 $t_1, t_2$），判定 $t_1 \sqsubseteq t_2$ 还是 $t_2 \sqsubseteq t_1$（p.3）。
3. **复杂度**：一般形式的包含问题是 NP-Complete 或 co-NP-Complete（NP 完全：计算机科学里「已知没有快速解法」的一类问题，规模一大就算不动）[19]；**幸好 MQTT 对 topic 层级与通配符的限制把复杂度降到多项式时间——本文进一步给出线性时间算法**（多项式/线性时间：解题步数随输入规模按比例增长，「规模翻倍、耗时翻倍以内」，工程上算飞快）（p.3, p.5）。这正是 SSF 可行的根基。

## 五、消息分发机制（p.3–5）
### 5.1 PF 与 SF（p.3–4）
1. **Publication Flooding（Fig.6, p.4，未提取）**：把每条发布消息泛洪给所有 broker（保证任何 broker 上都有全量消息）；订阅只在 subscriber 直连的 broker 本地处理。订阅者无论连哪个 broker，感兴趣的发布总会在本地出现。**最直接，但流量随消息量爆炸**（p.3–4）。
   **图解（Fig.6，未提取）**：几个 broker 方框连成网络；一个客户端向直连的 broker 发布一条消息后，这条消息被复制成多份、同时沿所有 broker 间连线向四面八方扩散，最终每个 broker 手上都有一条，各自的本地订阅者从中取走。读图结论：**不管有没有人要，每条发布都走遍全网每条边**，总流量 ≈ 每条消息 ×（broker 数 − 1）。与毕设的关系：若毕设采用「边云全量转发」，就属于这一类，简单但边缘带宽吃得最狠。
2. **Subscription Flooding（Fig.7, p.4，未提取）**：泛洪每条订阅；每个 broker 维护「topic → 感兴趣的邻居（客户端+broker）」映射；发布消息沿**精确路径**只发给需要它的邻居。**发布期流量省了，但订阅泛洪本身有成本**（p.4）。
   **图解（Fig.7，未提取）**：与 Fig.6 方向相反——这次铺满全网的是订阅：客户端向直连 broker 订阅后，这条订阅被逐跳复制给所有邻居 broker；此后每条发布不再乱窜，而是沿当初订阅铺好的「回程路」精确投递，箭头只指向需要该 topic 的方向。读图结论：**订阅贵一次（泛洪），之后每条发布都走最短需达路径**——发布量大时省；订阅频繁、兴趣分散时铺路本身反而亏。与毕设的关系：Mosquitto bridge 的「向固定邻居定向转发订阅」本质就是它的特例（p.2）。
    - SF 有一个显然优化——不转发重复订阅（Banno [6] 已暗示）；**本文刻意用「朴素版」SF 做对比基线**，因为该优化可视为 topic 包含的一个特例（p.4）。
3. **退订（unsubscription）的处理（Fig.8, p.4，未提取）**：比想象中 tricky——收到退订时 broker 不能简单删记录：只要还有客户端或**至少两个**邻居 broker 仍需要该 topic，broker 与邻居的订阅关系不变；仅当**无客户端且只剩一个**邻居 $b'$ 还需要时，原 broker $b$ 对 $b'$ 的订阅才可以撤销（此时 $b$→$b'$ 变成单向依赖）（p.4）。

### 5.2 Selective Subscription Forwarding（p.4–5）
- **核心思想**：MQTT 本质是 topic 中心的；PF/SF 不看 topic 层级，导致大量冗余订阅泛洪全网。SSF 保证 **broker 间的订阅永不重复、永不重叠**：转发前先做包含判定（p.4）。
- **数据结构（p.4）**：每个 broker $b$ 维护三个映射：
    - $TI_b$：topic → 感兴趣的邻居 broker/客户端集合；
    - $HT_b$：每个下一跳 broker → 它感兴趣（经 b 转发可达）的 topic 集合；
    - $HS_b$：每个下一跳 broker → **b 实际向它转发过**的 topic 集合（$HS_b \subseteq HT_b$）。$HS_b$ 与 $HT_b$ 的差就是「被包含而省掉转发」的部分。
- **Algorithm 1（SSF 主流程，p.4）**要点：
    1. 收到订阅 s：存入 $TI_b$；对每个邻居 $b'$，若 $HS_b(b')$ 中已有 $t_s' \sqsubseteq t_s$（已有订阅覆盖新订阅）→ **不转发**（pass）；反向若已有订阅被新订阅包含 → 先向该邻居退订旧的、再转发更宽的 s；其余邻居加入泛洪组 F 转发 s（**selective flood**）。
    2. 收到发布 p：查 $TI_b(t_p)$，精确转发给需要的 broker 集合 $B'$ 与客户端集合 $C'$（p.4）。
    3. 收到退订 us：从 $TI_b$ 删除来源；若 $TI_b$ 对该 topic 变空，对每个仍被转发过该 topic 的邻居，从 $HT_b(b')$ 中找出**被 us 包含的极小覆盖集 T**（当年因被 us 包含而没转发过的订阅），**现在把它们补发出去**（subscribe），再撤销 us、泛洪退订——保证既不冗余也不缺失（p.4）。**图解（Fig.9，未提取）**：5 个 broker 排成一条链，订阅从一端进入、覆盖范围从窄到宽：$s_2 \sqsubseteq s_1 \sqsubseteq s_3$（s2 的频道范围完全落在 s1 里，s1 又落在 s3 里）。看图要点：转发更宽的 s3 时，它包含（覆盖）了已转发的 s1、s2，链路不再补发窄订阅；而当 s3 退订时，箭头反向把 s1、s2 逐个「补回来」，保证覆盖不断档。读图结论：**broker 间订阅像取并集——只留最宽的、永不重叠；退订时把被它盖住的窄订阅还原**，这是 SSF 防漏报的关键动作（p.5）。
- **Algorithm 2（topic 包含判定，p.5）**：利用 MQTT 两条语法约束（只有 `+`/`#` 两种通配符；`#` 若出现必须是最后一个字符），把两个 topic 按 `/` 切成列表逐层比对，四种关系（相同 / t1 包含 t2 / t2 包含 t1 / 无包含），**运行时间 $O(\min\{|l_1|, |l_2|\})$ 线性**（$O(\cdot)$ 读作「数量级是……」；$l_1$、$l_2$ 是两个 topic 按 / 切开后的层数，$\min$ 取较小者——最多比「层数较少一方」那么多次，topic 只有几层时瞬间出结果）。**含义**：topic 层级数通常不大，判定不构成负担；**正是这个线性判定让 SSF 从「理论好看」变成「工程可行」**（p.5）。

## 六、性能评估（p.5–8）
### 6.1 无重叠订阅场景：SF vs PF 的解析与实测（p.5–6）
- 该场景下 SF 与 SSF 行为相同（没有可省的订阅）→ 本小节 SF 即代表 SSF（p.5 脚注）。
- **两个建模参数（p.5）**：
    - **IBR（Interested Broker Ratio）**：系统中对某 topic 感兴趣的 broker 占比——兴趣越分散 IBR 越低（两个参数合称 [[IBR 与 SPR（流量权衡两参数）]]）；
    - **SPR（Subscription Publication Ratio）**：订阅总字节数 / 发布总字节数之比。
- **解析式（p.5，Eq.1–5）**：PF 总流量 $T_{PF} = (m-1)\sum_i P_i$；SF 总流量 $T_{SF} = N_{P'} + (m-1)\sum_j S_j$。逐符号说明：$T_{PF}$、$T_{SF}$ = 两种机制下 broker 间网络的总流量；$m$ = broker 总数；$P_i$ = 第 $i$ 条发布消息的大小（PF 里每条发布都要复制过每条 broker 间边，共 $m-1$ 条边，所以乘 $m-1$）；$N_{P'}$ = SF 中发布沿精确路径投递的流量（只走有订阅者的边）；$S_j$ = 第 $j$ 条订阅的大小（SF 里订阅同样泛洪全过每条边）。大白话：**PF 是「消息遍地发」，流量 ≈ 消息总量 × 边数；SF 是「订阅先铺路、消息走专线」，流量 = 发布专线流量 + 订阅遍地发的流量**（p.5）。均匀分布简化后得到**拓扑无关的比值**：
$$\frac{T_{SF}}{T_{PF}} = \frac{IBR \times m - 1}{m - 1} + SPR \quad (5)$$
    - **式 (5) 拆开看**：左边 $T_{SF}/T_{PF}$ = SF 总流量是 PF 的几倍（< 1 即 SF 更省）；右边第一项 $\frac{IBR \times m - 1}{m - 1}$ = 订阅泛洪摊到每条边的相对成本（感兴趣的人越少、网络越大，这项越接近 IBR 本身，SF 越划算）；第二项 $SPR$ = 订阅总字节相对发布总字节的体积比（订阅越「便宜」SF 越划算）。大白话：**SF 划不划算 ≈ 「感兴趣的人占多少」加「订阅比发布贵多少」，与网络长什么形状无关**（p.5）。
    - **含义**：SF 是否划算只取决于兴趣广度（IBR）与订阅/发布体积比（SPR）——判定 SF vs PF 不需要具体拓扑，数边即可（p.5）。
- **7-broker 实测 testbed（p.6）**：7 个 Eclipse **Mosquitto** broker（最流行的轻量级开源 MQTT broker，C 语言编写）跑在 Docker 容器里 + 2 个客户端容器；**Wireshark 抓包**（网络抓包工具：把网卡上经过的数据包原样录下来逐个统计）算真实流量。结果（Fig.10, p.6，未提取）与理论趋势一致：
    - **右上区域（IBR 低、SPR 低）SF 省流量**——订阅泛洪总量远小于发布泛洪，而感兴趣 broker 又少；
    - **左下区域（SPR 大、多数 broker 感兴趣）PF 占优**；
    - **实际场景长期偏 SPR 低**——客户端订阅一个 topic 后通常会持续收到发布（p.6）。
    - 实验 vs 理论的偏差来源：**Mosquitto 会投机性地把短时间到达的多条订阅合并进一个包**（message grouping），把分界线向左下推移；论文给出按 50% 合并概率半修正的预测（Fig.10(c)）（p.6）。
    - **图解（Fig.10，未提取）**：横轴 SPR（订阅/发布字节比）、纵轴 IBR（感兴趣 broker 占比）的平面被一条理论分界线切成两半——右上区域（订阅体积小、感兴趣的 broker 少）SF 总流量更低，左下区域（订阅体积大、几乎人人感兴趣）PF 更优；三个子图分别为理论预测、7-broker 实测、按 Mosquitto「订阅合并」修正后的预测。读图结论：实测与理论趋势一致，但 Mosquitto 把多条订阅合并进一个包（相当于暗中帮 SF 再省一笔），实测分界线比理论线更偏左下。与毕设的关系：毕设评估 broker 间转发方案时，可照搬这套「两个参数扫平面 + 理论线对照实测」的画法（任务6）。
- **三种基本拓扑（Fig.11, p.6，未提取）**：linear（线性链）、binary tree（二叉树）、star（星形）；Fig.12 累计流量（未提取）：SPR=1 是 **SF 的最坏情形**（偏袒 PF），SF 在线性拓扑下泛洪开销大但发布期省流量。**结论：发布越集中密集，SF 越划算（把峰值流量从发布期挪走）；反之 PF 占优**（p.6）。

### 6.2 重叠订阅场景：千级 broker 仿真（p.6–8）
- **仿真设置（p.6）**：SimPy 框架（Python 的离散事件仿真库：按事件逐步模拟系统运行）；**1000 个 broker** 随机连成无环图，挂 **8000 subscriber + 2000 publisher**；每个客户端 1 msg/s；topic 池 100 个 topic、最多 5 层、每层 5 种表达（$5^5 = 3125$ 种不同 topic）；通配符概率：单层 `+` 概率 $\alpha$、多层 `#` 概率 $\beta$，测试设 $\beta = 1/10\alpha$，$\alpha \in \{0, 0.1, \dots, 0.9\}$（p.6）。
- 通配符率的影响机理（p.6）：对 PF 几乎无影响（发布反正全泛洪）；对 SF——通配符越多订阅兴趣越宽、要投递的发布越多；对 SSF——通配符越多重叠越多，正是 SSF 的发力点。
- **流量结果（Fig.13/14, p.6，未提取）**：SF/SSF 的输出流量随时间**递减**（新订阅越来越可能被旧订阅包含）；**最坏情形 $\alpha=0.9$（$\beta=0.09$）下：SF 比 PF 省 60% 网络流量，SSF 比 PF 省 81%**（p.7）。
- **吞吐与时延（Fig.15, p.7；Fig.21, p.8，均未提取）**：SF/SSF 吞吐先降后平（初期瓶颈链路拥塞、未订阅的发布被丢弃）；**SSF 收敛更快、占用带宽更低**（p.7）。服务时延单条消息高度集中于中位数附近：**平均时延 PF = 204.4、SF = 126.3、SSF = 100.8（时间槽）——SSF 比 PF 降 51%、比 SF 降 20%**（p.8；提取文本中 126.3 与 100.8 为移位编码，已按字符偏移还原，且与正文「51% 与 20% 降幅」互洽）。**反直觉提醒：网络很空闲、处理时延主导时，PF 反而时延最低**（p.8）。
- **订阅节省的干净度量（Fig.16/17, p.7，未提取）**：为剔除通配符带来的额外发布干扰，单独监控输出订阅：**SSF 只需泛洪 12%–18% 的订阅**（SF 不随通配符率变化）；以「订阅流量占总流量比例」计，**SSF 比 SF 降 42%–73%**（通配符率 0→0.9）（p.7）。这两条直接支撑摘要的「>40% 订阅流量节省」。
- **队列与累积收益（Fig.18/19, p.7，未提取）**：broker 队列设为无限，队列内数据量即负载。SSF 的队列内订阅不仅峰值更低而且**下降得快得多**；SF 从峰值线性缓降。**机理：订阅逐跳传播时每跳都可能撞上一个已包含它的订阅而止步——包含判定的收益随网络变大而累积**（p.7）。
- **诚实披露的弱点（Fig.20, p.8，未提取）**：构造订阅者分布集中的情形（网络缩到 1/10 规模以便展示，数字与前面不可比），**SF/SSF 泛洪订阅也能造成热点，峰值队列甚至超过 PF**；热点取决于订阅的时空分布，**出现位置 largely at random**（p.7–8）。

## 七、讨论（p.8）
- 与传统大规模发布/订阅的消息分发（高效路由/多播 [22][23]）的关系：那些工作只优化订阅方或依赖难以泛化到分布式边缘 MQTT 的架构（p.8）；泛洪之外还有 UDP 扩展、SDN 多播支持 MQTT 的路线 [24]–[26]（p.8）。
- **共存与一致切换（co-existence and unanimous switching）**：让 PF/SF/SSF 同时启用并按需切换是值得研究的方向；为可靠端到端送达，**路径上所有 broker 必须对每个 topic 处于同一模式**——因此切换只能是渐进过程，部分 broker 可能要在一段时间内跑混合模式（某些 topic 用 PF、其余用 SF）；MQTT 场景尚无标准共识建立机制，但其他场景的方案可推广（p.8）。

## 八、结论（p.8）
- 为把 MQTT 扩展到分布式边缘，本文研究了消息分发这一基本问题：梳理 PF/SF，提出 SSF——借线性时间的 MQTT topic 包含判定，只转发未被已有订阅包含的订阅。
- 实验 + 仿真（小规模 7 broker、大规模 1000 broker）表明：**SSF 同时做到订阅流量降 40%+ 与服务时延降 20%**，且不引入显著计算开销（p.8）。

## 局限与提取缺口
1. **假设网络无环**（p.3）：有环拓扑要先靠外部机制（如 MQTT-ST）破环——SSF 本身不解决环。
2. **包含判定收益依赖订阅重叠度**：订阅互不包含时 SSF 退化为 SF（p.5），无收益；订阅集中时反而可能造成超过 PF 的随机热点（p.7–8）。
3. **仿真假设理想化**：无限队列（p.7）、随机无环图、固定 topic 池 3125 个——broker 崩溃、会话持久化、QoS 差异均未涉及；实验只到 emulation（emulation 里 Mosquitto 的订阅合并优化还污染了理论对照，p.6）。
4. **提取缺口**：**本篇 PDF 无任何提取图**（图源目录 `figs/8/` 为空）；Fig.1–Fig.21 全部未提取，关键架构图（Fig.3 三层架构）与机制图（Fig.6/7 PF/SF 流程、Fig.9 SSF 演示）已在正文用文字描述。Fig.4 与 Fig.21 的部分数字在提取文本中是移位编码，已按统一字符偏移还原，并与正文百分比（51%/20% 降幅）交叉核对一致；Fig.10–20 的坐标轴刻度数字无法全部可靠还原，笔记只引用正文明确陈述的数字。
