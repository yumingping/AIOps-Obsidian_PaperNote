## 一、preview（p.1）
### 痛点：调用图有「盲点」，RCA 就瞎了
#### 1. 现有多源 [[微服务根因分析（microservice RCA）|RCA]] 默认「全量 trace 覆盖」
	（RCA = Root Cause Analysis，根因分析：故障发生后，从海量监控数据里定位「到底是哪个组件的什么问题引发了这次故障」的技术。）
	先交代可观测性三件套，全文反复用到：metrics（指标：CPU 利用率、请求延迟这类按时间采集的数值序列，装个监控代理就能采，不用动业务代码）；logs（日志：程序运行时打印的文本记录，同样免改码）；traces（调用链：一次用户请求在多个微服务之间逐级传播的完整记录，需要专门的分布式追踪埋点才采得到，是三件套里最难收的）。
	它们靠 trace 构建[[服务调用图（service call graph）]]，再把 metrics/logs 挂到图上做诊断。
	**这不行！** 微服务系统快速演化，新服务/新版本上线时工程师来不及做分布式追踪埋点；还有闭源组件、不支持 tracing 的服务——这些服务没有 trace，**不出现在调用图上**，成为[[盲点服务（blind spots）|盲点]]。

![[9-Fig1_p2.png]]
*图1（p.2）：带盲点的服务调用图示例——实线圆圈是有 trace 的服务，虚线圆圈（Ads、Shipping、Cart、Cart Database）是无 trace 的盲点，它们在靠 trace 建图的方法里直接隐形。*

**图解**：这是一张网络图（带箭头的服务调用关系图），画的是一个典型电商微服务系统。怎么看：最上方两个用户图标把请求发进 Front-end（前端入口），箭头一律从「调用方」指向「被调用方」；实线圆圈（Front-end、Recommendation、Checkout、Payment、Product Catalog、Email、Currency 等）是有 trace 埋点的服务，虚线圆圈（Ads、Shipping、Cart、Cart Database）是没埋点的盲点，右上角图例（Legend）说明了这两种画法。读图结论：盲点不是系统边角的无关服务——Cart 数据库承接 Cart 的数据读写、Ads 挂在 Front-end 下游、Shipping 参与下单链路，都在核心调用路径上。这些服务一旦出故障，靠 trace 建图的方法既「看不见它们存在」（图上根本没有这个节点），也无法把它们的 metrics/logs 挂到图上分析——这正是本文要解决的调用图不完整问题。
#### 2. 监督式方法要大量标注数据（[[标签稀缺]]）
	依赖 GNN/CNN（Graph Neural Network / Convolutional Neural Network，图神经网络/卷积神经网络：把服务图或指标序列直接喂给深度网络、端到端学出根因的一类方法）的多源方法需要大规模人工标注——每个历史故障案例都得先由人工标出「真根因是谁」才能当训练样本。
	**这也不行！** 系统天天变、旧故障修完新故障又来，历史标注覆盖不了未来的边角故障；系统规模大（有的多达 1500 个服务），全量标注成本高到不现实。
#### 3. 侵入式方法要求改源码
	如 Nezha（一个把 trace 和 log 联合起来做诊断的系统）要求每条日志都带 trace_id（贯穿一次请求全程的追踪标识：日志带上它才能逐条对应到调用链上的具体一步），这就得手改所有服务的日志/打印语句。
	**还是不行！** 对黑盒组件、第三方服务、尚不支持分布式追踪的新框架，这根本不可行。

### 新方法
TORAI：**不构建调用图**的无监督多源 RCA（[[无拓扑根因分析（topology-free RCA）]] 路线）。流程直觉版：先从可用的[[多模态观测（metrics、logs、traces）|多源遥测数据]]（metrics/logs/traces，缺哪样都行）量化每个服务的**异常严重度**；再用聚类把「症状相似」的服务分组；组内做因果分析排出粗粒度根因服务；最后用假设检验产出**细粒度根因指标**（具体哪个 metric/log/trace 模板异常）。

### 关键 trick
**绕开调用图这个假设本身**——既然图注定不完整，那就干脆不用图做骨架，改用「严重度向量 + 聚类 + [[因果发现（causal discovery）]] + 假设检验」的组合——因果发现（causal discovery，一类从纯观测数据里自动推断「变量之间谁导致谁」的统计算法族，不需要人工给出关系图）；假设检验（hypothesis testing，先假设「一切正常」，再看观测数据偏离该假设有多极端，极端到足够罕见就推翻假设、判定异常）。缺失的数据源严重度直接填 0，天然兼容盲点；metrics 和 logs 不用改代码就能采集，所以最坏情况下（100% 盲点）也能只靠这两样干活。

## 二、introduction（p.1–5）
1. 现实痛点：微服务故障代价巨大——Amazon 一小时宕机可损失高达 1 亿美元（p.1）；
2. 遥测三件套里 **trace 最难收**：
	- metrics：时间序列，CPU/内存/响应时间等，监控代理即可采集；
	- logs：半结构化文本，记录运行时事件；
	- traces：树结构，记录用户请求的[[调用链（calling chain）|调用序列]]，**需要分布式追踪埋点、常常要改微服务源码**（p.1–2）；

### 本文贡献（p.3）
1. 系统梳理现有多源 RCA 的三大局限（全量 trace 假设、依赖标注、侵入式埋点）；
2. 提出 TORAI：无监督、无需调用图、无需标注、无需改源码的细粒度 RCA；
3. 大规模实验：3 个基准系统 270 个故障案例 + 某大型互联网服务商 10 个真实故障，对比 9 个 SOTA（State of the Art，当前最先进水平的已发表方法）基线；真实故障上 top-3 推荐准确率 100%（p.3）。

### 关键术语（Sec 2.1，p.3）
- **Failure**：服务无法执行其功能；
- **Fault**：failure 的根因（CPU 过载、内存泄漏、网络断连…）；
- **Anomaly**：failure 的可观测症状；
- **粗粒度根因** = 根因服务；**细粒度根因** = 根因指标（具体 metric/log/trace）。

3. 工程量的量级：工程师给单个组件埋点要花数小时只覆盖几十行代码（Shen et al.）；有的系统多达 1500 个服务（p.4）；
4. eBPF（Linux 内核可编程追踪技术，无需改应用代码即可采集系统事件）也不保险：TraceWeaver 明确承认 eBPF「不足以解决追踪问题」，因为「无法保证应用会把追踪头传给相关的后端请求」；行业报告确认盲点在生产系统中普遍存在（p.4）；
5. 三个路线各自的死穴（p.2、p.4–5）：
	- 依赖全量 trace 建调用图 → 盲点让图不完整，关键 metrics/logs 挂不上图，行为没法分析；
	- 监督式（Eadro、DiagFusion 等）→ 标注不现实；
	- trace-log 紧耦合（Nezha）→ 黑盒/第三方组件不可能做到；
6. 有趣的旁证：有些不需要紧耦合的多源方法干脆**完全不用 trace** [66,67] 或**完全不用 log** [69]——又浪费了可用的数据源（p.5）。

## 三、TORAI 方法（p.5–9）
流水线六步：Transform → SeverityScorer → SymptomCluster → CausalRanker → RankAggregation → FineGrainer。

六步各自的输入输出（前一步的输出就是后一步的输入）：
1. **Transform（数据变换）**：输入原始 metrics/logs/traces 遥测数据 → 输出每个服务对齐后的多源时间序列，并按异常检测时刻切成正常段/异常段；
2. **SeverityScorer（严重度打分）**：输入各服务的多源时间序列 → 输出每个服务的严重度向量 $[\rho_m, \rho_l, \rho_{tc}]$（三个数据源各一个分数，缺失的源填 0，盲点服务照样有向量）；
3. **SymptomCluster（症状聚类）**：输入全体服务的严重度向量 → 输出按严重度从高到低排好序的服务簇（簇级排名）；
4. **CausalRanker（因果排序）**：输入每个簇内各服务的多源时间序列 → 输出该簇内部服务的因果排名（谁最像根因）；
5. **RankAggregation（排名聚合）**：输入簇级排名 + 各簇内部的因果排名 → 输出全体服务的粗粒度根因总排名；
6. **FineGrainer（细粒度定位）**：输入总排名靠前服务的各条指标序列 → 输出细粒度根因指标（具体哪条 metric/log/trace 异常）及其偏离分数。

![[9-Fig2_p6.png]]
*图2（p.6）：TORAI 全流程概览——从多源时间序列到严重度向量、聚类、因果排序、排名聚合，最后输出细粒度根因。Service 2 就是盲点（缺 trace 数据源，对应格画成空框「⊐⊐」）。*

**图解**：这是一张多面板流程图，A–G 七个面板用箭头串起整条流水线。怎么看：面板 A「Collect and Transform Telemetry Data」把三类原始数据按服务归拢——metrics（CPU/Mem/Latency 的小波形图标）、logs（「failed to handle」这类日志行）、traces（/call-s3、HTTP 500 这类操作记录）；面板 B「SeverityScorer」输出一张表格，每行一个服务、三列分别对应 $\rho_m/\rho_l/\rho_{tc}$，单元格颜色从绿色（Normal 正常）渐变到红色（Critical 危急），注意 Service 2 那一行的 trace 格是空框「⊐⊐」——它就是盲点；面板 C「SymptomCluster」把服务框进红、绿两个组（红 = 高严重度簇）；面板 D「CausalRanker」对每组服务做因果排序；面板 E「RankAggregation」把簇排名与簇内排名拼成全体服务总名单（Service 1 → 5 → 2 → 4 → 6 → 3）；面板 F「FineGrainer」给排名靠前服务的每条指标打分（CPU 0.73 最高）；面板 G 输出最终结果——带分数的细粒度根因列表（Service 1-CPU 0.73）。读图结论：盲点服务 Service 2 全程留在流水线里（B 面板有它的行，trace 格空着也不影响后面任何一步），这是「缺哪样都行」设计的可视化证据；整张图也能看清每一步的输出恰好是下一步的输入。

### 数据变换（Sec 3.1，p.5–6）
1. **Metrics**：采集 SRE（Site Reliability Engineering，站点可靠性工程：用软件工程方法做系统运维的理念，从业者也叫 SRE，约等于「会写代码的运维工程师」）总结的四大黄金信号（four golden signals：SRE 实践中公认最能反映服务健康度的四类指标）——Traffic（每分钟请求数）、Saturation（CPU/内存利用率）、Latency（平均响应时间）、Errors（失败请求率）（p.5）；
2. **Logs**：
	- 用 Drain（一个广泛使用的日志模板解析算法：把变量替换成占位符、把相似日志归并成同一条模板，例如「POST /api/order 200 12ms」「POST /api/order 200 15ms」都归并成「POST /api/order <*>」）解析成日志模板（去掉变量部分）；
	- 只统计**模板出现次数**按时间戳分桶成时间序列；
	- **不搞语义提取**——作者引实证研究说日志语义质量没保证且费算力（p.5）；
3. **Traces**：只用 trace 里的**延迟和状态码**转成时间序列（每个 trace 操作的频率）；**明确不建调用图**，因为图可能不完整（p.6）；
4. 每个服务得到多源时间序列 $X^i = \{X^i_M, X^i_L, X^i_{TC}\}$（下标 $M$/$L$/$TC$：metrics / logs / traces 三源序列组），按异常检测时刻 $\hat{t}_A$（**A**nomaly，系统判定异常发生的时刻）切成正常段（$t_0 \le t < \hat{t}_A$，$t_0$：正常期起点）和异常段（$\hat{t}_A \le t < \hat{t}_A+T$，$T$：异常窗长）。

### SeverityScorer：异常严重度打分（Sec 3.2，p.6–7）
1. **严重度偏离量**：对每条时间序列，先在正常期学均值和标准差，再衡量异常期每个点偏离多远：

$$a^{(i,j)}_t = \frac{x^{(i,j)}_t - \mu^{(i,j)}}{\sigma^{(i,j)}}$$

    - **含义**：$x_t^{(i,j)}$（服务 $i$ 第 $j$ 条序列在 $t$ 时刻的取值）、$\mu^{(i,j)}/\sigma^{(i,j)}$（该序列正常期的均值 / 标准差）。第 i 个服务第 j 条序列在 t 时刻偏离正常均值几个标准差——本质是 z-score（标准分：把「偏离了多少」统一换算成「偏离了几个标准差」的量纲无关分数，0 表示正好在平均水平，偏离越大越异常）；
    - **为什么需要**：给「这个服务病得多重」一个可计算的量。
2. **严重度分数**：异常期内取最大值：

$$\rho^{(i,j)} = \max_{\hat{t}_A \le t < \hat{t}_A+T} a^{(i,j)}_t$$

    - **含义**：$\rho^{(i,j)}$（服务 $i$、第 $j$ 条序列的严重度分数：异常窗内的最大 z-score 偏离）。

3. **严重度向量**：每个服务得到 $[\rho^i_m, \rho^i_l, \rho^i_{tc}]$（metrics / logs / traces 三源的汇总）：
	- metrics、traces：内部各序列的分数**求和**；
	- logs：因为各服务日志模板数差异太大，改**取最大**（最异常的那个模板分数）（p.7）；
	- **关键 trick**：数据源缺失就填 **0**——盲点服务照样有向量，整条流水线不断（p.7）。

	> 人话：盲点服务没有 trace，就当这条成绩是 0 分继续参赛——流水线绝不因缺数据而中断。代价是「没数据」和「真没异常」在向量里长一个样，这个歧义交给后面的因果分析兜底。
4. 注意：SeverityScorer 不直接找根因，只负责快速评估严重度、帮后面的组件聚焦异常服务（p.6）。

### SymptomCluster：症状聚类（Sec 3.3，p.7）
1. 用 [[高斯混合模型]]（GMM = Gaussian Mixture Model：假设数据点由若干个高斯分布——钟形概率分布——混合生成，算法反推出每个分布的中心和各点的归属概率，最常用的自动聚类方法之一）对严重度向量 $\{[\rho^i_m, \rho^i_l, \rho^i_{tc}]\}$ 做聚类；
2. 簇数 k 用 [[贝叶斯信息准则]]（BIC = Bayesian Information Criterion：给模型打分的指标——拟合得越好分数越低、参数越多罚得越重，折中防止把簇数调到过拟合）自动选：遍历所有可能的 k，取 BIC 最低者（p.7）；
3. 每个簇按簇内平均严重度（即高斯分布均值）排序，输出**簇级排名**——高严重度簇优先排查，符合「先看病重的」的运维直觉；
4. GMM 是**软聚类**：「弱异常」服务可概率性地同时进多个簇，不漏掉跨簇的因果关系（p.7）；
5. **为什么需要**：直接对全部时间序列做因果发现又慢又差（引 [45]），先用聚类缩小战场、降低 CausalRanker 开销。

### CausalRanker：因果排序（Sec 3.4，p.7–8）
1. 信念：**根因服务未必异常最猛**，但与受害服务有 cause-effect 关系，且这种关系体现在时间序列数据里（p.7）；
2. 对每个簇内的多源时间序列，随机分成小块（chunk：把一整段很长的观测序列切成若干小段，逐段分析，避免一次喂给算法算不动）；
	- 为什么分块？同时分析所有时间序列计算上太贵，且已被证明会降低性能 [45]（p.8）；
3. 每块用 **Ψ-PC**（Psi-PC：经典 PC 因果发现算法——PC = Peter-Clark 算法，通过反复做条件独立性检验、给变量之间连出「谁导致谁」箭头的主流因果发现算法——的升级版，额外能处理含干预、含失败的数据分布）建因果图：
	- 因果图 = 有向无环图（DAG = Directed Acyclic Graph：「有向」指箭头有方向、「无环」指沿箭头走不会绕回起点——因果图必须是这种形状，因为一件事不能直接或间接成为自己的原因），节点是时间序列（如 CpuUsage、ErrLog），有向边是因果关系（如 CpuUsage → ErrLog）；
	- **入度为零的节点**（interventional target）= 根因候选（p.8）；
4. 递归合并各块的根因再重复，直到只剩一个 chunk（分治思想，与 RCD [25] 同源——RCD 是一个分治式根因分析方法：先把指标序列递归切块、各自做因果发现再逐层合并，是本文 CausalRanker 的直接思想来源，也是实验基线之一）；
5. 最终按（条件）独立性检验分数排序：**分数越低 → 因果影响越强 → 越像根因**（p.8）；

	> 人话：把一簇服务的指标曲线交给因果发现算法，画出「谁指向谁」的箭头图；没有箭头指进来的节点就是头号嫌疑人——其余多半是它的下游症状。整图太大算不动，就切成小块分别画、再递归合并，分而治之。
6. 相对已有方法的两个进步（p.8）：
	- 先聚类、只对相关序列做因果分析（前人全量做，已被证明不行）；
	- 不再只靠因果发现出细粒度结果（RCD 用 Ψ-PC、CausalRCA 用 DAG-GNN——用图神经网络直接从数据中学出 DAG 结构的因果发现方法——单打独斗），另配 FineGrainer 做假设检验。

*图3（p.7）：CausalRanker 示例——「Service 1-CPU」是因果图中无父节点的根，它引发了 Service 1 的错误日志（ErrLog）和延迟（TraceLat）异常，于是 Service 1 被定为该组的根因服务。*

**图解**：这是一张上下两段的示意图，演示 CausalRanker 如何把一簇服务的时间序列变成因果排名。怎么看：上半部分是一个 3×3 的时序网格——行是同一簇的 Service 1、2、5，列是 CPU、ErrLog、TraceLat 三条序列，Service 1 的三条曲线在尾部集体抬升（时间上有先后），Service 2/5 的曲线则是全程剧烈抖动；大箭头表示把这 9 条序列交给因果发现算法，下半部分是产出的因果图：5 个圆形节点，Service 1-CPU 旁带红色的 Root cause 标注箭头，箭头从它指向 Service 1-ErrLog 和 Service 1-TraceLat，再由 Service 1-ErrLog 指向 Service 2-TraceLat、Service 1-TraceLat 指向 Service 5-TraceLat——根因的异常顺着箭头「流向」了下游受害者的指标。读图结论：没有任何箭头指进来的源头节点（Service 1-CPU）被判定为根因，其余节点全是它的下游症状；同一个服务的不同指标可以分别作为节点各查因果，这正是 TORAI 能同时给出服务级排名和指标级线索的原因。

### RankAggregation：排名聚合（Sec 3.5，p.8–9）
1. 规则：先按簇级排名（SymptomCluster），簇内再按因果排名（CausalRanker），拼成总排名；
	- 例：簇排名 [Group A, Group B]，A 内部 [a,c]、B 内部 [e,p,t] → 总排名 [a,c,e,p,t]（p.8）；
2. 细节考量：对**所有**簇都跑 CausalRanker，不只跑最高 severity 簇——因为最高簇可能只有一个服务，真根因可能藏在第二高簇（p.9）；
3. 兜底行为：若根因本身异常不猛（如代码缺陷只在下游显症），TORAI 会把受害服务排前面，让运维沿它们快速回溯真根因（p.9）。

### FineGrainer：细粒度根因指标（Sec 3.6，p.9）
1. **假设检验**：零假设 $H_0$ =「该指标时间序列在 $\hat{t}_A$ 后分布不变」。对每条指标序列，用正常期（$t_0$ 到 $\hat{t}_A$）的**中位数 med 和四分位距 IQR** 度量偏离：

$$a_t = \frac{x_t - med}{IQR}, \qquad \gamma = \max_{\hat{t}_A \le t < \hat{t}_A+T} a_t$$

    - **含义**：$med$（正常期中位数，median）、$IQR$（正常期四分位距，InterQuartile Range）、$a_t$（$t$ 时刻相对中位数的标准化偏离）、$\gamma$（异常窗内最大偏离统计量）、$H_0$（零假设：该指标在故障后分布不变）。γ 越大，拒绝 $H_0$ 的证据越强，该指标越可能是根因指示器；
    - **为什么不用均值/标准差**：异常检测时刻 $\hat{t}_A$ 常常不准——故障先发生、检测后触发，真正的异常点会混进「正常期」污染 μ 和 σ；**中位数和 IQR 对这种离群点鲁棒**（p.9，图4）。

![[9-Fig4_p9.png]]
*图4（p.9）：FineGrainer 对不精确异常检测时刻的鲁棒性——故障在 $t_A$ 发生，检测在 $\hat{t}_A$ 才触发，CPU 的「正常期」被离群点污染；μ/σ（0.05/0.8）被带偏，而 med/IQR（0.04/1.14）稳得多。*

**图解**：这是一张双指标折线图，横轴是时间、纵轴是指标取值，蓝线为 CPU、橙线为 TraceLat（trace 延迟）。怎么看：图中两条竖虚线——黑色 $t_A$ 是故障真实发生时刻、红色 $\hat{t}_A$ 是异常检测触发时刻，故障先发生、检测后知后觉，两条线之间的离群波动会被算进「正常期」；左下角标注的是这段被污染「正常期」的统计量（CPU：μ=0.05、σ=0.8；med=0.04、IQR=1.14），右侧标注的是故障期统计量（μ=1.29、σ=3.09；med=0.37、IQR=1.61）。读图结论：同样一段被离群点污染的数据，均值/标准差与中位数/四分位距给出的「正常水位」不同——μ/σ 对少数极端值敏感、容易被带偏，med/IQR 只看数据中间 50% 的部分、几乎不动；这就是 FineGrainer 在检测时刻 $\hat{t}_A$ 经常不准的现实下改用 med/IQR 的理由。曲线形态本身（故障后 CPU 与 TraceLat 双双跳升并持续高位震荡）也直观展示了什么叫「指标分布变了」。

## 四、实验（p.9–19）
### 研究问题（p.10）
- RQ1 粗粒度 RCA 有效性；RQ2 细粒度有效性；RQ3 效率；RQ4 组件消融；RQ5 真实场景。

### 数据集与设置（p.10–11）
1. 三个基准系统部署在 Kubernetes（开源容器编排平台：自动负责大量容器的部署、伸缩与调度，是微服务实验的事实标准底座）五节点集群（p.10–11）——Online Boutique（Google 开源的电商微服务演示系统）、Sock Shop（Weaveworks 开源的在线购物演示系统）、Train Ticket（开源火车票订票演示系统）都是社区常用的 RCA 基准：

| 系统 | #服务 | #指标 | #日志模板 | #trace操作 | #故障类型 | #案例 |
|---|---|---|---|---|---|---|
| Online Boutique | 11 | 77 | 33±9 | 17 | 6 | 90 |
| Sock Shop | 11 | 74 | 67±53 | **-（无trace）** | 6 | 90 |
| Train Ticket | 64 | 376 | 163±44 | 148.3±26 | 6 | 90 |

> **怎么读这张表**：一行一个基准系统，六列依次是服务数（系统里有多少个微服务）、指标数（共采集多少条 metrics 时间序列）、日志模板数（logs 解析后得到多少种模板，±是各服务间的波动）、trace 操作数（trace 里出现多少种操作）、故障类型数、故障案例总数。三个看点：① Sock Shop 的 trace 操作数是「-」——整个系统压根没埋 trace，这就是 100% 盲点的实验设定；② Train Ticket 64 个服务、376 条指标，比另外两个大一个量级，专门考察真实规模下的表现；③ 每系统 90 案例 = 6 类故障 × 若干注入位置 × 每组合重复 3 次，统计上够稳。

2. 数据采集：Prometheus（主流开源时序监控系统）+ cAdvisor（逐容器采集 CPU/内存等资源指标的守护进程）+ Istio（服务网格组件：在服务间通信上自动加一层代理，从而拿到调用级指标）采 metrics；Datadog Vector（开源日志采集管道）+ Loki（受 Prometheus 理念启发的日志存储与查询系统）采 logs；Jaeger（Uber 开源的分布式追踪系统）采 traces；负载 40–50 请求/秒（p.10）；
3. 故障注入 6 类：CPU hog（CPU 被打满）、memory leak（内存泄漏）、disk IO stress（磁盘读写打满）、socket stress（套接字连接占满）、network delay（网络延迟）、packet loss（丢包）；stress-ng（stress next-gen，Linux 下著名的资源压力测试工具，可单独打满 CPU/内存/磁盘）打资源、tc（traffic control，Linux 内核自带的流量控制工具，可人为加延迟、丢包）打网络；每组合重复 3 次 → 每系统 90 案例（p.10）；
4. **基准系统自带盲点**（p.11）：
	- Online Boutique：11 个服务只有 7 个有 trace（4 个盲点）；
	- **Sock Shop：完全没埋点（100% 盲点，压根建不出调用图）**；
	- Train Ticket：64 个服务只有 27 个有 trace（37 个盲点）；
5. 评价指标 $AC@k$（前 k 个结果含真根因的概率，k=1/3/5 对应「第 1 名就中」「前 3 名内中」「前 5 名内中」）与 $Avg@k$（average@k：前 k 个推荐位置按排名倒数加权平均的命中率——第 1 名命中记 1 分、第 2 名命中记 1/2 分……，比 AC@k 更奖励「把真根因排得更靠前」）（p.11）：

$$AC@k = \frac{1}{|A|}\sum_{a \in A} \frac{\sum_{i<k} R_a[i] \in V^a_{rc}}{\min(k, |V^a_{rc}|)}$$

    - 记号约定：$A$（故障案例集合）、$R_a[i]$（案例 $a$ 推荐名单的第 $i$ 位）、$V^a_{rc}$（案例 $a$ 的真根因服务集合）。T1/T3/A5 = AC@1/AC@3/Avg@5，是后文所有结果表格的列名；每实验跑 5 次取均值，t 检验（t-test：判断两种方法的分数差是否大到无法用随机波动解释的统计检验）p<0.05（差异显著性的通行门槛）才加粗。

### 基线（p.11–12）
1. 9 个基线：
	- **依赖调用图的多源方法**：PDiagnose（投票）、HeMiRCA（指标-trace 异常分单调相关，不用 log）；
	- **指标类因果方法**（不需要图）：CausalRCA（DAG-GNN 学因果图 + PageRank 打分——PageRank 即 Google 给网页重要性排序的经典算法：被指向越多、指向者越有分量，分数就越高，这里用来给根因候选排序）、MicroCause（PCMCI + 随机游走——PCMCI 是面向时间序列的因果发现算法族：同时检验跨时间滞后的因果关系与同期变量间的条件独立性）、RCD（分治 + Ψ-PC）；
	- **图+假设检验**：CIRCA（需给定调用图，回归式假设检验）；
	- **纯假设检验**：BARO（中位数/IQR 非参数检验，Fastest）；
	- **trace 类**：MicroRank（个性化 PageRank——带重启向量的 PageRank 变体——+ Spectrum：源自传统故障定位的频谱法，按「组件在成功/失败请求中出现比例的差异」给组件打嫌疑分）、TraceRCA（spectrum 频谱分析）；
2. Eadro、DiagFusion 等因需标注数据、Nezha 因需 trace_id 埋点而无法公平对比，未纳入（p.12）。

![[9-Fig5_p10.png]]
*图5（p.10）：实验平台示意——负载生成器 + Kubernetes 集群 + 故障注入器（CPU hog、内存泄漏等），多源遥测数据统一交给数据采集器。*

**图解**：这是一张实验平台架构图，左侧大框是 Kubernetes Cluster（容器集群），右侧是 Data Collector（数据采集器）。怎么看：集群内部画着被测系统的调用关系——Front-end（前端入口）的箭头指向 service 3 和 service 2，service 3 再连 service 3-database，service 4、service 1 接在 Front-end 下方，这是三套基准系统的缩影；两条红色箭头（标注 CPU hog、Memory leak）从集群外戳进 Front-end 和 service 2，代表故障注入器按剧本往指定服务打故障；右侧 Data Collector 旁画着波形图和文档图标，标注 Multi-source Telemetry Data（多源遥测数据），表示 metrics/logs/traces 被统一收走。读图结论：实验里的故障不是自然生产事故，而是工具主动注入的可复现故障（同一剧本可重放 3 次）；采集器把三源数据同时收齐、喂给所有对比方法，保证大家拿到同一份输入——这是后面对比实验公平的前提。

### 粗粒度 RCA 结果（RQ1，p.12–14）
1. **TORAI 三套数据集全部第一**：
	- Online Boutique（Metric+Log+Trace）：T1/T3/A5 = **0.83 / 0.95 / 0.93**；最好的指标类基线 CausalRCA 仅 0.21/0.68/0.60（p.12）；
	- Sock Shop：**0.84 / 0.96 / 0.94**；多源版 RCD 仅 0.39/0.73/0.66（p.13）；
	- Train Ticket：A5 = **0.89**，远超 CausalRCA（0.43）、CIRCA（0.46）、RCD（0.64）（p.12、p.14）；
2. **Sock Shop 是照妖镜**（p.13–14）：PDiagnose、HeMiRCA 这类靠 trace 建图的多源方法**直接没法跑**（全系统都是盲点）；TORAI 只用 metrics+logs 照样 A5=0.94；
3. 大系统优势更明显（p.14）：Train Ticket 64 服务，TORAI 各故障类型 A5 = CPU 0.83 / MEM 1.0 / DISK 1.0 / SOCKET 0.93 / DELAY 0.66 / LOSS 0.92；
4. 对比设计启示：CausalRCA、RCD 等把所有时间序列丢进因果图再靠 PageRank/随机游走/检验打分，没有聚类和严重度预筛，是掉分主因（p.12）。

### 细粒度 RCA 结果（RQ2，p.14–15）
1. Online Boutique 上 TORAI 平均准确率 **0.68**，第二名 BARO 只有 0.39（p.15）；
2. 有趣观察：假设检验类（BARO）和因果类（CausalRCA、CIRCA）在细粒度上都各有强项；TORAI 把因果（CausalRanker）+ 聚类（SymptomCluster）+ 假设检验（FineGrainer）合体，整体最好（p.15）；
3. Sock Shop：CIRCA A5=0.67 vs TORAI 0.69，差距缩小但 TORAI 仍领先（p.15）。

| RCD | 3.91 | 2.96 | 20.87 |
| PDiagnose | 3.24 | 1.26 | 61.53 |
| MicroRank | 77.56 | - | 91.04 |
| HeMiRCA | 62.08 | 55.38 | 206.02 |

### 消融（RQ4，p.16–17）
1. 各组件单独用 vs 完整 TORAI（p.16 表9，Metric+Log 设置）：

> **怎么读这张表**：前三行是流水线三个组件各自单独上场（不做聚类预筛、不做排名组合）的成绩，最后一行是完整 TORAI；每列 T1/T3/A5 = AC@1/AC@3/Avg@5。对照要点：CausalRanker 单独用在大系统 Train Ticket 上 T1 只有 0.09（几乎等于乱猜），拼进完整流水线后升到 0.74——「先严重度聚类缩小战场、再因果排序」的组合才是关键；SeverityScorer 单独用已能拿到 0.80/0.93/0.91（Online Boutique），接近完整版，说明按严重度排序本身就是一条强基线；FineGrainer 在 Sock Shop 的 T1 只有 0.07（逐条指标检验太碎，排不出服务级名次），完整版 0.84——三个组件互补，缺谁都明显掉分。

2. **CausalRanker 单独用最惨**（Train Ticket T1 仅 0.09）——纯因果学习不看严重度不行（p.17）；
3. SeverityScorer 只按严重度均值排名、不考虑服务间因果结构，FineGrainer 只做逐序列假设检验，都低于完整 TORAI（p.17）。

### 真实故障（RQ5，p.17–18）
1. 某大型互联网服务商生产系统，服务 5000 万+ 用户，组件分 5 类（OSB = Oracle Service Bus，甲骨文的企业服务总线——部署在系统入口处承接和转发外部请求的中间件组件；service/DB/Docker/OS 依次是业务服务、数据库、容器层、操作系统层组件）；因保密只提供 metrics+traces、无 logs；10 个故障，每个 5 分钟，根因经工程师确认（p.17）；
2. 结果（p.18 表11）：

| 方法 | AC@1 | AC@3 | AC@5 | Avg@5 |
|---|---|---|---|---|
| BARO | 0.70 | 0.90 | 0.90 | 0.82 |
| CIRCA | 0.20 | 0.50 | 0.70 | 0.46 |
| PDiagnose | 0.60 | 0.80 | 0.80 | 0.74 |
| RCD | 0.10 | 0.20 | 0.20 | 0.16 |
| **TORAI** | 0.60 | **1.00** | **1.00** | **0.88** |

> **怎么读这张表**：10 个真实故障案例，AC@1/AC@3/AC@5 = 真根因出现在推荐第 1/前 3/前 5 位的案例比例——案例只有 10 个、每个值 10%，所以表中数字只能是 0.1 的倍数；Avg@5 是前 5 位按排名倒数加权的命中率；加粗 = 该列最优。两点提醒：① 这份数据只有 metrics+traces（无 logs），重度依赖日志的方法天然吃亏；② 表中未列随机基线，但 AC@3 = 1.00 意味着 TORAI 在全部 10 个案例上都把真根因排进了前 3——对运维来说「前 3 名里必有答案」比「第 1 名命中 60%」实用得多。

3. 解读：TORAI AC@3 = **100%**、Avg@5 = 0.88；RCD 最惨（0.16），因为它无差别处理所有时序（[45] 指出的老毛病）；CIRCA 在全部时序上用 PC 算法建图，次优；BARO 靠纯假设检验有竞争力但不看因果和症状聚类（p.18）。

**图解**：这是一对折线图（左 Online Boutique、右 Train-Ticket），横轴都是盲点比例（Blind Spot Percentage，0–100%），纵轴是准确率（Accuracy，0–1.0），三条曲线分别是 AC@1（蓝色实线圆点）、AC@3（橙色虚线方块）、Avg@5（绿色点线三角）。怎么看：从左往右读就是「埋点被逐渐抽走、成绩如何变化」——重点盯两件事：橙线（AC@3）会不会掉，蓝线（AC@1）在 90%–100% 处是继续掉还是回升。读图结论：Online Boutique 上 AC@3 几乎全程贴着 0.9 以上，100% 盲点时仍有 AC@1=80%、AC@3=95%（正文数字）；Train-Ticket 退化平缓——Avg@5 从 89%（0% 盲点）降到最低 71.6%（70% 盲点），100% 盲点反而回升到 74%/84%，蓝线（AC@1）在 60%–90% 段落到约 0.6 的低位后于 100% 处翘头。「残缺 trace 比没有 trace 更误导」的结论就是从右图 90%→100% 的回升读出来的；整张图证明 TORAI 的成绩对盲点比例不敏感，最极端的全盲场景照样能用。

2. Online Boutique 几乎不掉点：AC@1 在 64.4%–88.9% 波动；**100% 盲点时仍有 AC@1=80%、AC@3=95%**——metrics+logs 足够（p.18）；
3. Train Ticket 平缓退化：Avg@5 从 89%（0%）降到最低 71.6%（70%），但 100% 盲点反而回升到 74%/84%——作者的解释很妙：**完全不完整、部分残缺的 trace 会引入噪声，全没有反而干净**（p.19）；

    > 人话：trace 像半张被涂花的地图——拿着残缺地图导航，有时比不用地图更危险。盲点比例升高时，「部分可信」的调用信息会误导排序；彻底没 trace 时 TORAI 干脆走纯 metrics+logs 的干净路线，成绩反而回升。
4. AC@3 全程比 AC@1 稳：真根因基本稳定在前 3，对运维足够实用（p.19）。

### 彩蛋：代码级故障（Sec 4.10，p.19）
1. 给 Online Boutique 的 cartservice 注入代码级故障（错误参数值，Int32 溢出）；
2. FineGrainer 把**堆栈跟踪**（stack trace，程序出错时抛出的调用栈文本；RedisCartStore.cs 第 54 行）识别为细粒度根因指标——因为其故障期出现频率显著偏离正常期中位数 0（p.19，图7/图8）；
3. 结论：只要故障在遥测数据里有症状（异常日志、错误 trace），TORAI 就能诊。

### 有效性威胁（p.20）
1. 假设「根因指标在故障后有显著分布变化」——有 prior 工作 [44,51] 和理论分析 [39] 支撑；
2. 明确**不假设根因服务异常分最高**：严重度聚类只是粗筛，最终由 CausalRanker 和 FineGrainer 定夺（p.20）。

## 局限与启发
1. **盲点不是被「修复」而是被「绕过」**：TORAI 不重建调用图，盲点服务上的故障只能靠其 metrics/logs 的统计特征诊断；涉及盲点的服务间传播路径仍然缺失——[[AIOps|AI 运维]]中「无图诊断」和「补图诊断」是互补路线，不是替代关系；
2. 严重度填 0 的设计简单粗暴：数据源缺失与「该源真的毫无异常」在向量里无法区分，全靠后续因果分析兜底；
3. 因果发现（Ψ-PC）仍依赖统计检验，时序短或噪声大时不稳——Train Ticket 的 DELAY 类故障 A5 只有 0.66，是六类故障里最弱一环（p.14）；
4. **对 AI 运维的直接启发**：与其逼所有团队补全 tracing 埋点（永远补不完），不如让 RCA 方法「有什么用什么」——metrics/logs 这类低成本数据的诊断价值被严重低估，Sock Shop（100% 盲点）实验是最好的证明；
5. 中位数/IQR 替代均值/标准差这类「统计鲁棒性小技巧」迁移成本极低，可直接抄进自研告警根因模块；
6. 与 [[拓扑感知]] 路线（论文12 Topo-MFP）正好相反：TORAI 证明「完全不利用拓扑」也能很高准确率，两者构成 C3 内部最有张力的对照。

## 与其他论文的关系

| 论文 | 观测假设 | 方法骨架 | 与本文的关系 |
|---|---|---|---|
| 本文 TORAI | **允许盲点**，可不建调用图 | 严重度聚类 + 因果发现 + 假设检验（无监督） | — |
| 论文12 Topo-MFP | 需要 trace 建动态服务依赖图 | 拓扑感知多模态传播图 + 反向随机游走 | **正面互衬**：Topo-MFP 把拓扑当软先验用足，TORAI 把拓扑直接扔掉；分别押注「拓扑有诊断价值」和「拓扑不可靠时怎么办」 |
| RCD / CausalRCA / BARO | 指标类，不依赖图 | 分治因果发现 / DAG-GNN / 假设检验 | TORAI 的组件来源与主要手下败将；单独用都不如组合 |

1. **与论文12（Topo-MFP）的互比是本部分最有意思的对照**。两者都是多源（metrics/logs/traces）微服务 RCA，但出发点针锋相对：Topo-MFP 假设 trace 可得，把服务调用拓扑做成**软先验**（拓扑相邻/远离的边用不同惩罚 $\rho_{in}/\rho_{out}$），学一张「诊断导向的传播图」再做反向随机游走；TORAI 从工业现实出发——trace 覆盖永远不完整——把调用图从方法里**彻底剔除**，只留时间序列层面的因果与统计检验。两者并不矛盾：若盲点比例高到图都没法看（Sock Shop、敏感性实验的 100% 端），TORAI 路线更稳；若 trace 覆盖尚可且传播路径本身是诊断关键，Topo-MFP 的 Hit@1 优势（比 raw 拓扑 RWR 高约 8–15 个百分点）说明拓扑信息值得用。
2. **与 B 部分的呼应**：B 部分处理「观测有误差的网络重构」——边可能漏记/多记，但仍想恢复一张完整的图；TORAI 代表另一种哲学：**承认某些节点永远观测不到，把问题重构为「不依赖完整图也能求解」**。这与 B 部分「从不完整图信号中学习图」的批量/在线方法构成方法论光谱的两端：一端补全观测，一端降低对观测的依赖。
3. 与 C1/C2 部分的关系：同属「观测或拓扑不完整下的故障诊断」主题，C1 侧更关注拓扑本身缺失/无拓扑的 RCA，C2 侧是电力网络的稀疏量测定位，本文「遥测数据天然不完整」的视角与它们互为参照：C1 的论文5 用[[虚拟拓扑（Virtual Topology）]]在无真实拓扑下兜底、论文6 完全无拓扑走事件驱动路线，C2 的论文7/10 补的是节点级缺失量测——与本文「节点存在但数据源缺失」的盲点问题共同拼出 C 区「缺什么」的完整光谱。
